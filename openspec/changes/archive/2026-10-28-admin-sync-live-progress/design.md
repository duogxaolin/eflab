## Context

The admin area and the sync worker exist (change `admin-sync-worker`): `SyncConfig` (enabled, `incrementalIntervalMin` 360, weekly full window, blocked-until), `SyncRun` (kind, trigger, status, timestamps, `stats` Json, `logTail` ≤ 64 KB), a 30-second worker tick with a 10-second heartbeat during a run, run-now buttons with 409 / 412 rules, and admin pages that poll every 3 seconds while a run is active. What is missing for the owner's request: the worker writes `stats` only at its checkpoint and its end (so a running run shows "No statistics yet."), nothing records which cards or images a run fetched (`newIds` / `changedIds` live in memory, the image file lists are deleted with the temporary directory), the dump and upload scripts print no per-image progress in the modes the worker uses, and the default interval is 360 minutes with no presets.

Constraints carried over: public repository, additive migrations only, `pg_dump` before a live migration, secrets only in the worker and masked per line, the order images → checkpoint → one transaction, a cancel after the rows committed is never recorded as cancelled, tests never touch the real source or the live database.

## Goals / Non-Goals

**Goals:** hourly incremental runs by default; live phase / progress / counters for a running run; a bounded record of the cards and images a run fetched with card names shown by the admin; presets and a link to the run after queuing; an operable hourly service on macOS.
**Non-Goals:** streaming (SSE / websockets); field-level diffs of changed cards; retention or per-card history across runs; changes to the request cadence, identity or concurrency toward the source; any public page; the seed and the cross-fill.

## Decisions

**D1 — Interval 60 by default, kept if customised.** One migration `ALTER TABLE "SyncConfig" ALTER COLUMN "incrementalIntervalMin" SET DEFAULT 60` and `UPDATE "SyncConfig" SET "incrementalIntervalMin" = 60 WHERE id = 1 AND "incrementalIntervalMin" = 360`, so an owner-set value (e.g. 180) is never overwritten; both statements are idempotent. The constant in `packages/shared/src/sync.ts` follows. The 15–1440 CHECK stays. Presets are plain buttons that fill the input (then Save as before). Cost of an hourly incremental run with nothing new: about 3 API requests (`/meta` + 2 pages, from the code map) and no image step — 72 requests a day. A run is still skipped while a run of its group is active, and the weekly full window still replaces the incremental run of that hour. Alternative rejected: a code-only default (the stored row would stay 360).

**D2 — `progress` is its own Json column, not more `stats` keys.** `stats` is `.strict()` and describes a finished run; mixing a changing live snapshot into it would blur "so far" with "final". `SyncRun.progress Json?` (null when not running): `{ phase, done, total|null, counters, updatedAt }`, schema `syncRunProgressSchema` (strict, bounded phase names per kind: check — "Asking the source"; incremental — "Reading pages", "Comparing images", "Downloading images", "Uploading images", "Writing the catalogue"; full — "Dumping", "Comparing rows", "Seeding", "Comparing images", "Downloading images", "Uploading images"). Written by the worker inside the existing heartbeat UPDATE (`UPDATE "SyncRun" SET "heartbeatAt" = …, "logTail" = …, "progress" = … WHERE id = … AND status = 'RUNNING'`) — so progress is at most 10 s old plus the 3 s poll, i.e. the "about 13 seconds" of the spec — and nulled in the final transaction. `ctx.setProgress(...)` and `ctx.stats` live updates are the only new handler API; handlers never write the row themselves. Alternative rejected: a progress table per run (more writes, no need for history).

**D3 — Image-step progress from the scripts.** The dump script's newest-first mode prints nothing per image and the image step prints every 500; the upload script prints every 500 files. Both get `--progress-every N` (default: off, output byte-identical to today — proven by running each script with and without the flag on the same fake data and diffing, plus unit tests of the line format) printing `PROGRESS <done>/<total>`; the worker passes `N = 20` for the dump and 50 for the upload (small relative to the 10-second write, bounded log volume) and parses the line in its existing `onLine` handler next to the upload summary regex. Lines contain numbers only. A line that does not match is an ordinary log line (redaction as today).

**D4 — `items` is a bounded Json column.** Shape `{ version: 1, cards: { new: {ids[], total, truncated}, changed: {…} }, images: { downloaded|overwritten|unverified|uploaded: {paths[], total, truncated}, failed|uploadFailed: {entries: [{path, reason}], total, truncated} } }`, every list ≤ 2,000, newest first, totals true; a CHECK `octet_length("items"::text) <= 524288` backs the size. Entries are ids and validated relative paths (`cards/<id>_<kind>.webp`, `emblems/<kind>/<hash>`), reasons are a closed set of classes (`http_<status>`, `timeout`, `bad_signature`, `too_large`, `host_refused`, `other`) — never a body, URL or header. Written by `ctx.recordItems(...)` at the incremental pre-write checkpoint (so it survives a worker dying after the commit) and rewritten in the final transaction; the image file lists (`images_new.txt`, `images_overwritten.txt`, `images_unverified.txt`, `images_failed.txt`, `image_errors.log`) and the upload results file are read before the run directory is removed. A full run fills `cards` from its row-digest comparison and `images` from its image step with the same caps. Alternatives rejected: a `SyncRunItem` table (no cross-run history wanted; unbounded growth), storing names (names are catalogue data that can change; join at read).

**D5 — Names joined at read time.** `admin.runs.get` collects the card ids it will list (first N rows of each card group, N = 50 per group, bounded), does one `Player.findMany({ where: { id: { in } }, select: { id, baseId, name, ovr/maxOvr, registeredPosition, cardType } })` and returns rows `{ id, baseId, name, overall, position, cardType }` plus the raw lists' totals; ids missing from the catalogue show as "card <id>". The run list does not carry items. `runs.get` stays no-store and admin-only.

**D6 — UI.** Run detail: a "Progress" block while queued / running (phase, `role="progressbar"` with `aria-valuemin=0`, `aria-valuemax=total`, `aria-valuenow=done`, `aria-valuetext="45 of 120 images"`; indeterminate = no `aria-valuenow`, text "Downloading images"), live counters from `progress.counters`, replaced by the final statistics when the run ends; "What was downloaded" below the statistics (collapsible groups, "None", "N more not listed"). Dashboard: the active run card shows phase + bar + counters and a link to the run; after `runs.queue` succeeds the response's run id is linked ("Run #N queued — open it"). Presets: a button row ("15 min", "30 min", "1 hour", "3 hours", "6 hours", "12 hours", "24 hours") that sets the number input; the current value's preset has `aria-pressed`. Tokens and components as the rest of `/admin` (no new palette); the bar fill uses the accent, the track the line colour, contrast ≥ 3:1 for the bar (non-text) and ≥ 4.5:1 for text; `prefers-reduced-motion` removes the indeterminate animation. Polling stays `ACTIVE_POLL_MS` (3 s).

**D7 — Hourly automatic runs on macOS.** The worker is a long-running process; "cron" would only start it. launchd keeps it alive (`docs/admin-sync.md` already carries the plist): `KeepAlive`, env file `~/.config/eflab/worker.env` (mode 0600, outside the repository, built by the orchestrator from the root `.env` without printing it), `ThrottleInterval`, logs under `~/Library/Logs`. The worker's first tick queues an incremental run if due, so the live interval is set to 60 before it is loaded. The Mac must be awake: runs missed while it sleeps are caught up on the next tick (the rule "last start older than the interval") but a missed weekly full window is not. Documented, not changed.

**D8 — Order of the live changes.** Pre-merge: agents run only against scratch databases (`eflab_synctest_*` style) and the fake source. Orchestrator after verify: backup, migrate (worker stopped), merge, rebuild web, restart API then web, create the launchd job, set the interval, watch the first run.

## Risks / Trade-offs

- Progress writes add a column to the 10-second UPDATE: negligible (one row, ≤ 1 KB). Items can reach 512 KB per run and 24 runs a day: ~12 MB a day worst case. Mitigation: the caps are far above a normal hourly run (a handful of cards); a run with no new cards stores a few bytes. Retention is out of scope, flagged in the docs (old runs can be pruned by hand).
- A script flag could change default output by accident → byte-for-byte default tests (spec "Defaults unchanged").
- An hourly source request pattern could trigger a block → unchanged politeness rules (stop at 403 / 429 / challenge, 6-hour block, no retry); the owner decided to run it.
- A sleeping Mac stops the schedule → documented.

## Migration Plan

Additive: `ALTER TABLE "SyncRun" ADD COLUMN IF NOT EXISTS "progress" jsonb`, `… "items" jsonb`, the `SyncRun_items_size` CHECK added only if missing (`DO $$ … IF NOT EXISTS (select 1 from pg_constraint …)`), the default change and the conditional update above. Tested on a scratch copy of the live database twice (idempotence) and from the empty baseline. Rollback (worker and API stopped): drop the two columns and the constraint, `SET DEFAULT 360`, delete the migration row; documented in `docs/admin-sync.md`.

**Third re-verify round (2026-10-28; 0 critical, 2 warnings, 4 suggestions — W1, W2, S1, S2, S3 addressed, S4 report-only)**

- **W1 — a raising handler could deadlock the pool; corrected.** The previous round's handler raised `StopRequested` at whatever bytecode the main thread was on. `concurrent.futures.as_completed()` (and `wait()`) begin by taking every future's lock (`_AcquireFutures`); an exception raised inside that loop leaves those locks held, the drain then waits on a running future whose worker blocks in `set_result` on one of them, and interpreter exit joins that worker forever. Reproduced deterministically with the stock lock loop made slow (every lock taken, a marker, 300 ms) on the previous round's scripts, rebuilt from its saved patch: both hang until SIGKILL. The fix:
  - **The handler never raises.** `_on_sigterm` only sets `_TERM["requested"]` (and restores the default action, so a second SIGTERM ends the script at once). The `busy` section and every `except StopRequested` around the pool are gone. `StopRequested` (exit 143) is raised from ordinary code, after the loop, once the stop is final.
  - **A wait loop with a bounded window — only with the flags.** `run_stoppable` submits at most *workers* items at a time, in order, and waits with `concurrent.futures.wait(…, timeout=0.25, FIRST_COMPLETED)`. The finished items of a round are taken in submission order, and the flag is read at least every 0.25 s even while every worker waits on a slow fetch. On the flag nothing more is submitted, anything still queued is cancelled, and the running items finish and are taken. Why the window: once the handler cannot raise, `as_completed` cannot deadlock either; the wait loop exists so the flag is read even when no item finishes, and every `wait()` round takes, then releases, every pending future's lock and waiter — O(pending) a round. With every file submitted up front that is O(n²) over a run (a first full sync of about 97,000 images), with the window O(workers) a round. Why the window equals the worker count: with one item queued behind the running ones, a freed worker would start it before the loop reads the flag (measured: 11 lines instead of 10 after a SIGTERM at 9 of 20), so with the window at the worker count nothing new starts once the stop is seen. Without the flags the loop is HEAD's `as_completed`, unchanged.
  - **Dump: the handler covers the image step only.** It is installed when the image section starts, when `players.jsonl` exists, and the default action is restored after `download_images`. The data phase (its `as_completed` page loop) never runs with the handler, so a SIGTERM there kills the script as before. The worker passes the flags only to its `--no-data` image steps, so nothing changes for it.
  - **S2:** the dump's last `PROGRESS` line is printed after the lists are written and after the stop is final, so a SIGTERM that arrives while the lists are written also counts.
