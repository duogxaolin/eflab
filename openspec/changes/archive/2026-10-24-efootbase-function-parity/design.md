The evidence is the outside-repo survey folder of 2026-10-23: S1 (player page and Progression, 11 loads), S2 (`/players`, 7 loads), S3 (home, palette, packs, compare, skills, 10 loads), S4 (one load stopped by a Cloudflare challenge; lists what is still unmeasured) and the earlier manager/booster check (5 loads). This change makes **no request to the reference site** and **no database write or migration**.

Current state that shapes the approach:

- The engine (`packages/shared/src/progression.ts`, `ovrModel.ts`) already reproduces every reading: 3,047/3,047 stats, 1,534/1,534 tiles, 285/285 faces, 195/195 point labels on the card page and 130/130 stats, 5/5 overalls on compare (at zero proficiency bonus). - Database facts checked read-only for this design:

## Goals / Non-Goals

**Goals:**
- Implement only reference behaviour verified by at least two independent checks, with the acceptance numbers taken from the survey and re-derived on the local data.
- Keep every older eFootLab URL readable; write the reference's parameter names where verified.
- Keep eFootLab's deliberate improvements the owner kept (honest counts, styled 404, `/packs/[slug]`, 72 cards per numbered page and the count line) and those that avoid reference oddities (listed below).

**Non-Goals:**
- Anything graded SINGLE, OBSERVED (1), CANDIDATE, NOT DETERMINED or not opened — see "Pending register".
- Data refresh (new cards, packs, Niko Kovač, manager order inside a rating) — the separate data update.
- The compare radar (two axes unsettled): unchanged.

## Decisions

### D1. What is in and what is out (evidence rule)
Only items marked VERIFIED in S1–S3 (or two loads of the manager/booster check) become requirements. Deliberate deviations from verified reference behaviour, each recorded as "reference oddity not copied":
- Jumping row offers both Aerial Strength and Goalkeeper 1 (reference: Goalkeeper 1 only; S1 itself lists it as an oddity).
- "+" never passes 25 per category (reference bug).
- A link without any category key and without `pts=0` opens the Max-OVR allocation (reference: any parameter → missing categories 0, so `?mp=85` loads an empty build). Consequence, accepted: a reference-written Reset link that carries other parameters but no `pts` (for example `?mp=80`) opens as the Max-OVR build on eFootLab. eFootLab's writer always writes `pts=0` for an empty build, so its own links round-trip.
- Over-budget or out-of-range links are corrected, the URL rewritten at once and the correction announced (reference: silent clamp, URL left wrong).
- Search under 3 characters shows the empty state / a hint (reference: an unrelated max-overall top list at 2 characters).
- Manager search stays accent-insensitive; skills search stays name-only with folding and keeps `q`/`group` in the URL (reference behaviours seen once).
- Home Escape keeps the APG order (first Escape closes, second clears) — the reference's "first Escape clears" was seen once.
- The phone keeps the Progression sheet (the reference showed none on one card; removing it would strand Max Level, the position selector and "About this build").

### D2. Card-page build codec in `@eflab/shared` (`build-url.ts`)
Pure functions `encodeBuildQuery(state, card) → URLSearchParams` and `decodeBuildQuery(params, card) → { state, corrections[] }`, unit-tested, used by `PlayerDetailClient` (and, with a side prefix, by compare). The writer follows the spec order `sho … gk3 pts ml mp mgr b1 b2 b2l`. The decoder:
1. reads category integers, caps each at 25, drops invalid values;
2. if neither a category key nor `pts=0` is present, uses the card's opening allocation for the link's Max Level (Max OVR for a level cap above 1; empty for a Highlight card with a level cap of 1, whose panel opens empty — the reference also reads `?ml=10` as an empty build);
3. cuts an over-budget allocation **in category order** (`clampAllocationInOrder`: each category keeps what the remaining budget buys) — this reproduces the reference's L10 reading (25/27/25 → 25/18/3 at 144 pts);
4. validates `ml`, `mp`, `mgr` (against the picker list once loaded — an unknown id is dropped and reported only after the list answered), `b1` against the card's levels, `b2` against the second-booster slugs and the card's own Booster 2, `b2l`.
Corrections produce one polite message and an immediate `replaceState`. URL writes go through the same echo-ref adoption as `/players`, so a `replaceState` never triggers a same-page navigation or a re-decode loop. The position selector stays out of the URL (the reference has no position parameter).
*Alternative considered:* the reference's exact reader (missing categories = 0 whenever any parameter exists) — rejected per D1; the advisor review and S1 both list it as an oddity.

### D3. Remembered manager
`localStorage["eflab:selected-manager"]` holds the id. Read only in an effect after mount (SSR renders the no-manager build; one re-render applies the stored manager), wrapped in try/catch. Precedence: build parameters in the URL decide alone (`mgr` selects without storing; no `mgr` = no manager); otherwise the stored id if it is in `manager.picker`, else it is removed. The picker query is enabled on mount when an id is stored, otherwise on the first opening (as today). Writing the URL is not triggered by the preselect (the plain URL means "this viewer's opening state", as on the reference's plain loads). Evidence for cross-card persistence: the manager check (load 1 → load 2, same profile) and the owner's own browser (the owner reported seeing a manager pre-selected); writing the key on selection is verified on five cards. Compare never touches the key (not observed there).
Deselect (choose again or "Clear") and a proficiency-control move remove the key; deselect sets the proficiency to 90 (S1 §6, verified on two cards from 90, 80 and 75).

### D4. Second booster, own Booster 2 and Booster 1 levels
- `@eflab/db` exports the fixture's basic boosters (ids 1–29, with stat vectors mapped through the existing fixture stat-key table) as `BASIC_BOOSTERS`; the API serves them as `booster.secondChoices` (public, cacheable, no DB access). The web never types the list.
- Slug helper `secondBoosterSlug(name)` in shared (rule in the spec; reproduces the one observed slug). Slugs of the other 28 boosters are eFootLab's own and recorded as unverified against the reference.
- Levels: `boosterAtLevel(booster, level)` in shared returns a vector with every non-zero stat set to `level`; the engine input receives the scaled vector, so the engine is unchanged. Trending is detected by `cardType === "TRENDING"`; the cycle is `[3, 0, 1, 2]` (all Trending usable boosters have magnitude 3; a Trending booster with another magnitude does not exist in the data — the UI then falls back to on/off and the case is listed as unmeasured).
- Own Booster 2 = a usable (non-empty) `booster2`; absent or empty `booster2` (ids 0 and 136 today) → "Select Booster". Own-Booster-2 intermediate levels (`b2l=1/2`) are SINGLE (one card) → not built; only `b2l=0`.
- The "Select Booster" slot (and `b2`) is offered on cards with a level cap above 1 only (`takesSecondBooster`, batch A): the S1 raw readings show the slot on Quaresma (L1) but **no booster row at all** on both Highlight cards with a level cap of 1 (L5 Messi "Gracias, Leo!", L9 Vitinha) and only Booster 1 on the Trending cards (L6, L11). A second-booster choice on a level-cap-1 Highlight card is therefore unmeasured and not built; a `b2` on such a card is dropped as not applicable.
- The drawer reuses `filters/Modal.tsx` (drawer variant) like `ManagerPicker`, with a pinned search field.

### D5. Level-cap-1 Highlight and Trending panels
- Highlight with `levelCap === 1`: the panel's level control is a 1–80 slider with −/+ (`ml`), budget `2 × (ml − 1)`; the engine receives `levelCap: 80` and `maxLevel: ml`. Categories, strip, Max OVR and Reset render from `ml ≥ 2`.
- Lowering any Max Level (this slider and the existing input for level cap > 1) uses `trimAllocationFromLast(alloc, budget)` in shared: remove one stat point at a time from the last category that holds points until the cost fits. It reproduces the S1 sequence (Messi ml 10 → 9 → 8 → 5). The previous "reset to zero when unaffordable" rule of the input is replaced by the same trimming (one rule, announced).
- Trending: a "Build" panel (manager + proficiency), stat rows plain, `b1` cycle in the booster row.
- Both include the proficiency bonus (default 90) in the face, stats and tiles, as the reference does at level 1 (three cards).
- Other level-cap-1 types keep today's note and no bonus (not measured).

### D6. One Adjust popover for rows and strip items
A single `AdjustPopover` (Popover primitive) renders, per category, − / value / + and a 0–25 range input whose `onChange` commits the largest affordable value ≤ the requested one. Opened from a stat row (its category; Jumping → two blocks) or from a strip item (240 px). Strip items become popover triggers (`aria-haspopup="dialog"`, `aria-expanded`); panel labels keep the pin with `aria-pressed`. While a popover is open its categories own the highlight and hover previews from other strip items are ignored. The per-stat breakdown moves into a "Stat breakdown" table inside "About this build" (26 rows: base, training, cut at 99, proficiency, boosters, manager, shown) — reachable by mouse, keyboard and touch, unlike a hover-only tooltip.

### D7. Tooltip timing
`TOOLTIP_OPEN_MS = 500`, `TOOLTIP_CLOSE_MS = 100`, warm window unchanged at 500 ms, focus opens immediately — constants in `components/ui/Tooltip.tsx`, defined once.

### D8. Search: one server rule
`player.search` input `{ q: 3..100 chars, page: 1..50 }`, output `{ rows: CardPreview[] (12), hasMore }`; `CardPreview` gains `packName`. SQL (index-backed, measured 1.5–8 ms on cote / messi / ronaldo / wonderkids / a no-match term):
```
WITH m AS (
  SELECT id FROM "Player" WHERE "nameNormalized" LIKE $pattern            -- GIN trigram
  UNION SELECT "playerId" FROM "PackCard" WHERE "packId" = ANY($packIds)    -- PK index
  [UNION SELECT id FROM "Player" WHERE "japName" ILIKE … OR "chineseName" ILIKE …]  -- non-ASCII only
) SELECT … FROM "Player" JOIN m USING (id) ORDER BY "maxOvr" DESC, id DESC LIMIT 13 OFFSET …
```
`$packIds` are computed in TypeScript: the API keeps `(id, normalizeSearchQuery(name))` of all packs in a 60-second in-memory cache and substring-matches the normalised query, so pack names fold exactly like the query (no SQL `unaccent` disagreement). `player.list` uses the same `m` fragment for its `q`. The tiered ranking and the fuzzy tier are removed. Shared `liftWordStartRows(rows, q)` reorders each page client-side (stable). The palette keeps its own empty state (`player.trending`, 12 newest distinct players — eFootLab has no live trending data).
*Alternative considered:* a trigram index on pack names / a `featured` column — needs a migration; rejected (no DB write in this change, and the PackCard path is already fast).

## Risks / Trade-offs

- [Old single-value `form`/`wfa`/`wfu` and `sort=highest` links change meaning] → documented as intentional in the spec; comma lists and every other legacy form keep their meaning; release note in CLAUDE.md.
- [The stored manager makes the first render differ from the hydrated one] → the stored manager is applied in one post-mount render; numbers are computed by the same engine, no layout shift beyond the values.
- [Search loses fuzzy matches that users relied on] → the reference has no fuzzy matching ("messi lionel" = 0 there); the pack-name match adds the reference's recall.
- [Pack cache up to 60 s stale after a seed] → packs change only on a full seed; acceptable, documented.
- [Removing home pack arrows hurts plain-mouse users] → rows stay scrollable by Tab, touch, trackpad and Shift + wheel; the reference has the same rows.
- [Route move `/skills` → `/wiki/skills`] → permanent redirects for every old URL and slug; links in the app updated in the same change.
- [Max Level trimming replaces "reset to zero" for cards with a level cap above 1] → one rule for every Max Level change, announced; spec scenario updated.
- [Compare cannot edit categories or boosters yet] → stated in the pending register; the URL still restores any per-side allocation a reference link carries.

## Migration Plan

No schema or data migration. Deploy = build `@eflab/shared`, `@eflab/db`, API and web; restart the API and web by port. Rollback = revert the merge commit; old URLs remain valid in both directions because the readers accept the legacy forms and the redirects are additive.
