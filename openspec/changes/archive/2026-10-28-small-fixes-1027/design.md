## Context

Three owner decisions of 2026-10-27 on items that earlier changes left open: raise the contrast of dimmed stat rows, enforce typed `<Link href>`, make the local database survive a reboot. `next.config.ts` already sets `typedRoutes: true` and `next-env.d.ts` imports `./.next/types/routes.d.ts`; the gap is that `tsconfig.json` excludes `.next`, so `.next/types/link.d.ts` (which narrows `Link`'s `href`) is never in the program (CLAUDE.md "Route types and `next-env.d.ts`", measured the same on Next 15.5.26 for a default `.next` build). Web and docs only; no API, database, worker or dependency change.

## Goals / Non-Goals

**Goals:** every dimmed stat text ≥ 4.5:1 with the highlight still readable; an unknown link fails `pnpm typecheck` and `next build`, never stale, changing no file of a served `.next` outside `<distDir>/types` and nothing the running server reads; the OrbStack step is documented truthfully; the key decision recorded.
**Non-Goals:** no change to the reference-matching layout, tier colours or accent ring; no new dependency; no compose change (verified: `restart: unless-stopped` is set and `docker inspect eflab-postgres` reports it); no history rewrite or key rotation.

## Decisions

**D1 — Contrast by measurement, not by guess.** The dim is `opacity: .4` on `.efb-stat-row[data-dim="true"]` (globals.css). An opacity blend of the text with the panel behind it lowers contrast for every colour, worst for the red (<70) tier `#ff2e2e` and the dim secondary text `#a0a0a0`. Steps: (1) compute, in a scratch script outside the repo, the blended colour of each text class over its real background (`--color-card` / `--color-default` / hover states, the value pills' tier backgrounds `statTierBg`, chips) for opacities 0.4…1.0 and list the contrast ratios; (2) take the smallest opacity for which every ratio ≥ 4.5:1; (3) if no opacity below 1 reaches it for some class (red tier on its pill), keep text at full colour and express the dim another way — e.g. dim only the row background / pill fill and drop the ring-less rows' icon/shadow — measured the same way; (4) confirm in the browser with axe-core 4.14 on a capped card in all four highlight states at 1440 and 390 touch; (5) record the numbers here ("D1 result"). The accent ring on highlighted rows is unchanged. The reference dims to .4; this is the owner's accessibility decision and goes in `openspec/ui-dna.md` → "Highlight" as a deviation.

**D2 — Typed links: tracked bridge file + `next typegen` before every check.** *(Superseded by the probes — see "D2 result" below: the bridge fails (b); Next's `experimental.strictRouteTypes` writes the import into `next-env.d.ts` for the active distDir instead, and the spec's "Framework Version And Bundler" is modified to allow that one key.)* Candidate (probed earlier): a tracked file in `apps/web` (e.g. `link-types.d.ts`) whose only content is `import "./.next/types/link.d.ts";`, included by tsconfig, with the web `typecheck` script running `next typegen` first so the file it imports always exists and matches the current routes. Things the implementation must establish by probe (record under "D2 result"): (a) that `next typegen` writes only below `<distDir>/types` — it does rewrite the type files of a served `.next` — and changes no other file of that build and nothing the running server reads (compare file lists and mtimes of everything else under `.next`, and `:3000` keeps answering); (b) how the import path follows `NEXT_DIST_DIR` — a check build that writes to `.next-check` must not type-check against a stale `.next/types`: if a fixed import path cannot be both fresh and distDir-agnostic, the options in order are `typescript.tsconfigPath` pointing a build at a generated tsconfig, a `next.config.ts` step that regenerates the types the bridge imports, or a `prebuild`/`pretypecheck` script; (c) whether `typedRoutes` needs anything else; (d) that the stricter program does not pull `.next/**` files in (no `exclude` change that makes tsc read the build output). If none of (a)–(d) can be satisfied together, STOP: write the exact reason here and in the spec as "not enforceable" with what would make it so, instead of shipping a check that can be stale.

**D2 result (2026-10-27) — enforced with `experimental.strictRouteTypes`, not with the bridge file.** Probes in a scratch git worktree outside the repo (node_modules cloned, never installed) unless noted. (a) `next typegen` writes `<distDir>/types/{routes.d.ts, root-params.d.ts, cache-life.d.ts, validator.ts, link.d.ts}` and nothing else (≈ 0.7 s); `next-env.d.ts` is rewritten only when its content differs. Against a *served* build (worktree `next build` + `next start` on :4200, warmed up): after `next typegen` the 568 other files under `.next` are identical (size, mtime to the nanosecond, sha256), the five type files byte-identical (new mtimes), 20 responses identical (7 pages and the 13 `/_next/static` scripts of the home page), and identical again with `.next/types` moved away — the server never reads it. ## Risks / Trade-offs

- A type check that needs generated files can break a clean clone → the clean-clone scenario is a gate (`pnpm typecheck` and the direct `next build` with no `.next`).
- Making rows more readable moves the page slightly away from the reference → listed as a deviation; the accent ring keeps the highlight obvious.
- Fixing links may touch several files; each is a typed correction with no behaviour change (checked by the router/history transcript of `next-16-upgrade` where relevant and a page smoke).
- `experimental.strictRouteTypes` contradicts the archived `web-platform-upgrade` spec's "no experimental key" → the delta MODIFIES "Framework Version And Bundler"; the main spec's **Purpose** paragraph still says "with no experimental flags", and a delta cannot change a Purpose, so at archive time it is edited by hand: the exact pinned version, Turbopack by default, and `strictRouteTypes` (types only) as the only experimental key (tasks.md 4.2).
- Every `pnpm typecheck` / `pnpm lint` rewrites the five type files under the served `apps/web/.next/types` → probed harmless (no other file of the build changes, the server never reads `types/`); a typecheck racing a `next build` of the same `.next` could read half-written type files.
