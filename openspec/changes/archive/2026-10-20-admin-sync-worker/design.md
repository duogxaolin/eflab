## Context

See `proposal.md` for motivation and `specs/` for requirements.

- Data flow today is manual: `scripts/efootbase_dump.py` (pages + images, polite, stops on 403/429/HTML), `scripts/r2_upload.py` (boto3), `packages/db/src/seed-efootbase-full.ts` (one transaction; replaces Country/Team/League/Pack/Skill/PlayerSkill/Featured*, upserts Player/Manager/Booster over a column list minus cross-fill columns). The seed already reads its input from `EFOOTBASE_DUMP_PATH`, `EFOOTBASE_META_PATH`, `EFOOTBASE_PACKS_PATH` and `EFOOTBASE_STATIC_DIR`; a seed run without `static/skills.json` erases skill metadata (CLAUDE.md, known limitations). Row mapping (`buildPlayerRow`, card-type map, skill key map, booster upsert) is private to the seed file.
- The API has `User`/`Session` for visitors (`eflab_session`, no sign-in UI), `protectedProcedure`, CORS with `credentials: true` from `WEB_ORIGIN`, and a web tRPC client that already sends `credentials: "include"`. The API process currently holds no efootbase or R2 secret.
- Facts about efootbase: `sort=time_added&order=desc` lists newest first; `time_added` does not change on stat edits; `total_count` is a lookahead; Cloudflare may answer 403/HTML; card image URLs are id-based and R2 serves objects immutable for a year.
- Shared Prisma connections are pooled, so a session-level Postgres advisory lock is unsafe across queries.

## Goals / Non-Goals

**Goals:**
- A single, safe executor of sync jobs with a durable queue, visible history and no secrets in the web or API process.
- Reuse of the existing, proven dump/upload scripts and the seed's mapping; the seed's behaviour stays exactly as is.
- Honest limits stated in the product (incremental sees only new cards; overwritten images need a version bump).

**Non-Goals:**
- Automatic eFHUB cross-fill, automatic image-version bumping, notifications, UI account management, roles, a compose service, changes to the visitor auth.

## Decisions

**1. Database model, additive migration.** `Admin`, `AdminSession`, `SyncConfig` (single row id 1, also holds `workerHeartbeatAt`), `SyncRun` (adds `cancelRequested`). Enums `SyncKind`, `SyncTrigger`, `SyncStatus`. Seed of the single `SyncConfig` row is done by the migration SQL (`INSERT … ON CONFLICT DO NOTHING`), so no seed run is needed. Index `SyncRun(queuedAt desc)`, `(status)`. No existing table changes. *As implemented (migration `20261019230000_admin_sync_worker`):* `SyncRun` also has a per-run `heartbeatAt` (the stale-run rule of the spec is about the run's own heartbeat; `SyncConfig.workerHeartbeatAt` stays the dashboard's liveness signal), `requestedById` (FK → Admin, SET NULL), `stats Json` (shape = `syncRunStatsSchema` in `@eflab/shared`, `.strict()` so no unlisted key can be stored) and `watermarkBefore/After`; `SyncConfig` has `blockedReason`, `updatedAt`, `updatedById`; `Admin` has `passwordChangedAt`, `failedLogins`, `lockedUntil`, `lastLoginAt`, `disabledAt`; `AdminSession` has `tokenDigest` (unique), `lastSeenAt`, `expiresAt`. Raw-SQL CHECK constraints back the Zod bounds (single row `id = 1`, interval 15–1440, weekday 0–6, hour 0–23, `octet_length(logTail) ≤ 65536`). Alternative: reuse `User.role` — rejected by the owner's choice and because visitor accounts and admin accounts have different threat models.

**2. One running run, enforced by a partial unique index.** Raw SQL in the migration: `CREATE UNIQUE INDEX … ON "SyncRun" ((true)) WHERE status = 'RUNNING'`. The worker claims work with `UPDATE … SET status='RUNNING' WHERE id = $1 AND status='QUEUED'` and treats a unique violation as "someone else is running". Alternative: `pg_advisory_lock` — rejected because Prisma pools connections, so a session lock may be released or held by an unrelated connection. Queue de-duplication (409) is checked in the API in a transaction against QUEUED/RUNNING rows of the same kind group (check separate from incremental/full).

**3. The worker is the only holder of secrets and the only caller of the source.** `apps/worker` loads the repo-root `.env` like the API (`tsx --env-file-if-exists`), reads `EFBASE_API_KEY`, `R2_*`, optional `EFBASE_API_BASE` (tests) and `SYNC_R2_UPLOAD_CMD` (tests). Child processes get an explicit minimal environment. A check is a single `fetch` made by the worker (same key header and user agent as the script, a constant noted as duplicated from the script and covered by a test that compares them); everything heavier shells out to the scripts. Alternative: the API calls the source — rejected: it would put the key in the web-facing process.

**4. Tick loop and pure scheduling.** *(Second verify CR1: every stored time is written through typed Prisma queries or `jsonb_to_recordset(… timestamp(3))`, never a raw `Date` parameter — a raw one is a timestamptz that Postgres converts with the session TimeZone; the worker suites run under America/New_York and Asia/Ho_Chi_Minh sessions.)* `setTimeout` loop every 30 s: write heartbeat, recover stale RUNNING rows (heartbeat older than 10 min → FAILED "worker restarted"), call the pure function `dueRuns(config, runs, now)` from `@eflab/shared` to queue scheduled runs, then claim the oldest QUEUED run and execute it. While a run executes, a second timer keeps the heartbeat fresh and polls `cancelRequested`. Weekly full window: the weekday-hour hour starting at `fullHourUtc`; due when no full run started at or after the window start of the current week. All times UTC. A run's "start" for scheduling is `startedAt ?? queuedAt` (a run cancelled while still queued counts as the attempt for its slot, so a cancel is not undone on the next tick); a due full run supersedes a due incremental one (they share one queue group); `blockedUntil == now` is no longer blocked. Implemented in `packages/shared/src/sync.ts` (`dueRuns`, `nextScheduledRuns`, `fullWindowStart`, `isStaleRun`, `isWorkerOnline`). Alternative: a cron library — rejected (no new dependency, logic is tiny and testable).

**5. Child-process helper.** `spawn(command, args[], { shell: false, env })`, line-buffered stdout/stderr into a ring buffer of 64 KB, redaction of every configured secret value before storage, SIGTERM then SIGKILL after 10 s on cancel or timeout (per-kind wall-clock limits: check 30 s, incremental 30 min, full 6 h). Python is `python3` (override `SYNC_PYTHON`).

**6. Incremental pipeline.**
   a. `efootbase_dump.py` gets new optional flags (defaults unchanged): `--newest-first-since EPOCH` — sequential pages with `sort=time_added&order=desc`, stop after the first page whose rows are all older than EPOCH, write `players.jsonl` atomically; meta/packs fetch stays available via existing code (the incremental run fetches `players_meta.json` each time for the card-type map). *As implemented:* `--newest-first-since EPOCH` keeps only cards with `time_added ≥ EPOCH`, de-duplicates ids shifted onto the next page by a card released mid-walk, also stops at the first short page, and aborts (exit 1, nothing written) if `time_added` ever increases along the walk (the API silently ignores unknown parameters, so an ignored sort must not read as "nothing new"); `--data-parts meta,teams,packs,players` (default all four) and the shorthand `--meta-packs-only` select the data endpoints (the incremental run uses `--data-parts meta,players`); `--key-from-env` reads `EFBASE_API_KEY` from the child's environment instead of a `.env` file; `--api-base URL` points the script at the fake server in tests.
   b. TS side loads the JSONL, validates like the seed (known card-type codes, known `s_*` keys, known booster stat keys; any unknown aborts the run as FAILED with the key named — never guess), maps rows with the shared mapping, upserts in one transaction: Player (excluded cross-fill columns), PlayerSkill for those players, Booster (insert missing, dump wins as in seed), and *missing* Country/Team/League (insert only, ids allocated like the seed does, matched by name). It never deletes and never touches Pack, FeaturedBundle, Skill, Manager.
   c. Images: `efootbase_dump.py --no-data --only-ids <inserted ∪ rewritten> --etag-vs-bucket R2_PUBLIC_BASE` into a temp dir for the cards this run inserts AND the existing cards it rewrites, plus the emblems of the countries / teams / leagues it inserts, then `r2_upload.py --no-resume` from that temp dir (it contains only new / differing files) with the usual key prefixes. A rewritten card's images are ETag-compared with the bucket like the full run's (decision 7) and only a differing one is downloaded and counted as overwritten (second verify finding CR2; `R2_PUBLIC_BASE` is therefore required — refused before any request without it). *Third verify:* an image that fails (any host) or is skipped because the third-party host pesdb.net refused (W1: its 403 / 429 / HTML skips only its own images, never blocks the source) no longer stops the write — the card is written, the image counted failed and its card id kept as owed (`stats.imagesPendingIds`, `imagesChecked: true`); every incremental / full run takes over the owed ids of the runs since the last one whose image step finished, compares those among its own cards and keeps the rest owed. "Overwritten" counts only a body that differs from a bucket object with a content-MD5 ETag (a body equal to it is dropped; a non-MD5 bucket ETag makes the replacement "unverified" — W2). *As implemented:* the images are fetched and uploaded BEFORE the write transaction, so a failed image step leaves the catalogue untouched and the next run sees the same cards as new. Source image URLs and emblem file names are checked first (verify finding C1: allow-listed https hosts per image kind — pesdb.net only for `transparent` under /assets/img/ (W-e) —, safe names; the dump script checks them again before any request or write) and the script's own checks run as a dry `--validate-only` pass over every fetched row before any image request or write (W-a), so nothing the script refuses can surface only later. *Cancel / time limit during the write (verify finding W3):* the signal is checked before the transaction, before each statement and as its last step (a throw rolls it back); the runner keeps the run RUNNING while the write is in flight (`ctx.writeCatalogue`, bounded by `CATALOGUE_WRITE_WAIT_MS` > the transaction's max wait + timeout) and never records CANCELLED once it committed (the abort is noted in the log, the outcome stays the handler's).
   d. Watermark before = `max(releaseDate)` in DB (as epoch seconds) − 7 days; after = the new maximum. The 7-day margin tolerates ties and late visibility; rows seen twice are simply upserted. With no release date in the database the watermark is null and the incremental run refuses to start (reading everything is the full run's job) — `incrementalWatermark` in `@eflab/shared`.

**7. Full pipeline.** Pre-flight: the static snapshot and ≥ 2 GB free disk, else FAILED before any request. Dump all pages into `os.tmpdir()/eflab-sync-<runId>` (mode 0700) with the existing script (4 workers, atomic output). Before seeding, compute, for every dump row, a hash of its mapped player columns and compare with the same hash computed from the database row (one read-only pass) → sets *new* and *changed*. Run the seed as a child process with the four location variables pointing at the staging directory and without `--prune`/`--reset-users`. After a successful seed, for new cards download images; for changed cards compare the CDN ETag with the object's ETag in the bucket (HEAD each, via a small flag added to the scripts) and download only differing images; upload with `r2_upload.py --no-resume` from the temporary images folder. Remove the staging directory in a `finally`. No cross-fill. *As implemented in the script:* the comparison flag is `--etag-vs-bucket <public bucket base URL>` — a HEAD on the bucket's public URL (no credentials) and a HEAD on the CDN; same plain-md5 ETag → skipped, different / bucket 404 → downloaded, an unusable answer → downloaded and counted as a possible overwrite; hash-named emblems already in the bucket are skipped without a CDN request; downloads that replace a bucket object are listed in `images_overwritten.txt` (the overwritten count). It assumes R2's ETag of a single-part upload is the content MD5 (S3 semantics; `r2_upload.py` uploads card images single-part) — not checked against the real bucket yet; if it does not hold, every card reads as changed (more downloads, never a missed change). **Staging-directory caveat found while proving the seed refactor:** the seed sets `Skill.iconKey` only when `EFOOTBASE_STATIC_DIR/skill-icons/<file>` exists, so the full run must point `EFOOTBASE_STATIC_DIR` at the real snapshot directory (or a copy that includes `skill-icons/`), otherwise the seed would clear every skill icon key; the pre-flight check (task 5.5) must therefore cover `skill-icons/` as well as `skills.json`. Documented trade-off: an image that changed while its row did not is not detected (in the 2026-10-18 re-dump 5,312 images changed against 5,380 changed rows, so the overlap is near-total; a manual dump remains the exhaustive path). *Second verify (as implemented):* before the seed the run (a) runs the dump script's `--validate-only` pass over players.jsonl + teams.json (W-a: what the image step would refuse fails the run before the catalogue is written) and (b) writes the ids it must compare — new ∪ changed ∪ the `imagesPendingIds` of every FULL run after the last OK one — to the RUNNING row's `stats.imagesPendingIds` (a checkpoint), removing them only when its image step finished (CR2: a card whose image step failed, was blocked, cancelled or killed after the seed committed is compared by the next full run although its row no longer differs; the admin API sends only their count, `imagesPending`). The seed child runs inside `ctx.writeCatalogue` and is not stopped by a cancel / time limit / worker stop (W-d): it ends on its own or after `SEED_CHILD_TIMEOUT_MS` (70 min; its transaction's own timeout is 60 min), the runner keeps the run RUNNING meanwhile, and a run whose seed committed is never recorded CANCELLED. Consequently a full run can outlast its 6-hour limit by the seed's remaining time, and a worker stop during the seed waits for it (service stop timeouts in `docs/admin-sync.md`). *Third verify:* the images compared are those of new cards, cards whose row differs (row digest) and owed cards (W3 — an image-only change on an otherwise unchanged card is not detected; a manual dump covers it); a failed / third-party-skipped image leaves the run OK with its card owed (W1); the seed's own "done" line also proves its commit (S5); the checkpoint before the seed must update exactly its RUNNING row or the run stops before the seed (S4).

**8. Shared mapping module.** `packages/db/src/efootbase-map.ts` exports the pure mapping (row → Player columns, field maps, card-type map builder, skill key resolution, booster object mapping, URL basename helpers, aptitude inversion) and the cross-fill column sets; the seed imports it. The refactor must keep the seed's output identical: `verify-seed.py` and row counts before/after on the live database copy (a scratch database restored from a `pg_dump`, never the live one) are the proof.

**9. Admin authentication.** Password hashing in a node-only module in `packages/db` (never imported by `apps/web`): `scrypt` via `node:crypto` with N=2^15, r=8, p=1, 16-byte salt, 64-byte key, encoded as `scrypt$N$r$p$salt$hash`; constant-time compare; a fixed dummy hash is verified when the user name is unknown. Cookie `eflab_admin` (random 32 bytes base64url; DB stores SHA-256 hex), `Path=/`, `HttpOnly`, `SameSite=Strict`, `Secure` outside development (same helper idea as the visitor cookie). Sliding expiry 12 h, absolute 7 d; `lastSeenAt` updated at most once a minute; expired rows deleted on each sign-in. Failure counting on the account row (`failedLogins`, `lockedUntil`); per-address limit in memory (20 per 15 min, keyed on `req.ip`; production deployments behind a proxy set Fastify `trustProxy`, documented). CSRF: mutations require `x-eflab-admin: 1` and an allowed `Origin`; the header is added only by the admin client wrapper and added to the CORS allowed headers. The `admin` tRPC router uses a new `adminProcedure`; the context resolves the admin session independently of the visitor session. Admin responses carry `Cache-Control: no-store`. *As implemented:* `@fastify/cors` keeps `allowedHeaders` unset, which reflects the preflight's requested headers for the allowed origins (so `x-eflab-admin` is admitted, verified by a preflight check) without narrowing what the public client may send; the admin session is resolved lazily (`ctx.getAdmin`, memoised per request) so public procedures pay no extra query; `adminProcedure` = no-store → 401 without a valid session → CSRF on mutations, `adminPublicProcedure` (sign-in only) = no-store → CSRF; a Fastify `onSend` hook also sets `no-store` on every `/trpc` URL naming an `admin.*` procedure (batches and early errors). Sign-in lower-cases the name, refuses a disabled or locked account only after the same scrypt work, does not count attempts while locked, and resets the counter when it locks. *Concurrency (verify finding C2):* every attempt first counts itself with one conditional UPDATE (`failedLogins = failedLogins + 1` unless disabled / locked, returning the row only then), runs one scrypt (the dummy hash when nothing was returned), and then either issues the session inside a transaction that re-reads the row `FOR UPDATE` and requires enabled, not locked and a streak — every counted attempt, in-flight ones included — of at most 5, or sets the lock with one conditional UPDATE when the streak reached 5; so a burst of parallel guesses cannot let a right one win, a success never clears a lock, and the unknown-name, malformed-name, wrong-password and locked paths run the same statements (W7; the counter's increment commits asynchronously so a counted attempt pays no extra WAL flush — equal within 0.1 ms on a scratch database, except the one lock-setting attempt; a Postgres crash can lose the last increments, the lock and the session are synchronous); `admin:set-password` and `admin:disable` also delete the account's sessions. The password module is `@eflab/db/admin-auth` (subpath export, not in the package index). Web and API must be the same *site* (for example subdomains of one domain, or localhost on different ports) because the cookie is `SameSite=Strict`; the docs say so.

**10. Admin web.** Client-rendered pages under `app/admin/` (`login`, `page`, `runs`, `runs/[id]`) that call `admin.me` first and show a neutral shell until it answers, so no admin data is in HTML; `next.config.ts` adds `Cache-Control: no-store` and `X-Robots-Tag: noindex` for `/admin/:path*`, each page also exports `robots: { index: false }`. A small `adminTrpc` client reuses the existing tRPC types with the extra header. Polling with `refetchInterval: 3000` while any run is QUEUED/RUNNING and `document.visibilityState === "visible"`. Full sync uses a native `<dialog>` confirmation (existing `Modal`). Styling follows `openspec/ui-dna.md`.

**11. Testing without the source.** A fake efootbase HTTP server (Node `http`, started by tests) serves `/players` pages from a small generated JSONL, `/meta`, `/packs`, image paths, and modes `403`, `html-challenge`, `slow`. Worker tests run against scratch databases, one per suite — `eflab_synctest_core` (`worker.test.ts`), `eflab_synctest_inc` (`incremental.test.ts`), `eflab_synctest_full` (`full.test.ts`); test mode accepts only names matching `eflab_synctest(_…)` on a loopback host — each created, migrated and dropped by its suite in the local Postgres container, and a stand-in upload command. The smoke test's admin section uses its own scratch database `eflab_smoke_admin_<pid>`. Pure functions (scheduling, watermark, redaction, password hash, config validation) have unit tests with tamper checks. Smoke additions cover the admin API's negative paths without any worker. One real source request (a check) is made manually during acceptance, with the owner's key from the existing `.env`.

**12. Operations.** Root scripts `worker:dev`, `worker:start`, `admin:create`, `admin:set-password`, `admin:disable`. `docs/admin-sync.md` explains running the worker as a service (launchd/systemd/pm2 examples without secrets), required `python3` + `boto3`, the secrets it reads, first-run checklist (create admin, run a check, run one incremental by hand, `pg_dump` before the first full), recovery and the limits.

## Risks / Trade-offs

- [Incremental misses edited cards] → weekly full run; stated in docs and in the dashboard help text.
- [A full run holds seed locks for minutes] → default window 03:00 UTC Sunday, backup recommended before the first one, the seed is one transaction so a failure leaves the catalogue intact.
- [Overwritten images look stale for a year in caches] → warning with count on the dashboard and run detail; the owner raises `DEFAULT_IMAGE_VERSION` and rebuilds (conscious tradeoff; automation is a later change).
- [Worker host needs Python + boto3 and a local copy of the static snapshot] → pre-flight checks with clear failure messages.
- [Brute force through many addresses] → per-account lock-out as well as per-address limits; passwords ≥ 12 characters; only the owner has accounts.
- [Seed refactor regresses the seed] → verified on a scratch copy with `verify-seed.py` and equal counts before accepting.
- [Upstream blocks us] → stop at once, `blockedUntil` 6 h, never bypass; the dashboard shows it.
- [Cookie SameSite=Strict breaks cross-site deployments] → documented same-site requirement.
- [Partial unique index is raw SQL outside Prisma's schema] → documented in the migration and checked by a test that tries to start two runs.

## Migration Plan

1. `pg_dump` of the live database (path recorded), then `pnpm db:migrate` adds four tables, three enums and the unique index; nothing existing changes.
2. Create the first admin with `pnpm admin:create`, start `pnpm worker:start`, open `/admin`, run a check, then one incremental run, then (after another `pg_dump`) a full run — all by the owner.
3. Rollback: stop the worker, drop the new tables (a down script is documented); public pages are unaffected throughout.
