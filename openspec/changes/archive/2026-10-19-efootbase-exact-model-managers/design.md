## Context

See `proposal.md` for motivation and `specs/` for requirements. State of the code on `main` (95278e6):

- `packages/shared/src/progression.ts` projects stats with `floor(s × rate)` proficiency rates, a level-86 special case, and an overall from fitted weights (`ovrWeights.ts`) plus a fitted proficiency penalty and a per-card anchor. `ProgressionPanel.tsx` owns the controls; `PlayerDetailClient.tsx` owns the state and takes Best Fit / "At XX" and the Pitch Map from `PlayerCardDTO.positionRatings` (cross-filled eFHUB columns, null for 2,284 newer cards). `CompareClient.tsx` also reads `positionRatings` for a tooltip.
- The player DTO already carries `height`, `weakFootAccuracy`, the 13 `positionAptitudes` (database coding 0 = full, 1 = half, 2 = none, inverted from the dump by `invertAptitude` in the seed) and `registeredPosition`. `Manager` has `rating`, `imageUrl`, `booster1Stat`, `booster2Stat` (our stat names) and `inPicker` (69 rows) but no order column; this change must not migrate, so the picker order is rating descending then id ascending.
- Evidence (read-only, outside the repository, under the session scratchpad `efb-survey/`): `scripts/oracle.py` reproduces the overall formula; `runs/*.json` hold 260 readings per card for five cards (26 final stats, 13 tiles, overall, slider, manager); `proficiency-bands.json` holds the band table for levels 77–90; `managers.json` holds the 69 managers. The weight table comes from efootbase's public client code; the owner accepted the terms risk.

Formula as recovered (the spec states the arithmetic; this records the table layout the data module must be re-keyed from): a 364-integer table `N` in 28 rows × 13 columns. Row 0 is height, rows 1–25 are the 25 stats in the order offensiveAwareness, ballControl, dribbling, tightPossession, lowPass, loftedPass, finishing, setPieceTaking, curl, heading, defensiveAwareness, tackling, aggression, kickingPower, speed, acceleration, physicalContact, balance, jumping, gkAwareness, gkReach, gkCatching, gkParrying, gkReflexes, stamina; row 26 is weak-foot accuracy and row 27 is defensiveEngagement. A position's column is found through two small index tables in `oracle.py` (`TT` from position index to a code, `II` from column to code); the data module must store the weights per position name so application code needs no index tables.

## Goals / Non-Goals

**Goals:**
- One exact model shared by the panel, the Pitch Map, Best Fit and the compare tooltip, verified against every measured reading, with tests that fail when a constant or rule is altered.
- A manager picker with the measured effect and honest UI.
- Nothing from efootbase committed except integer tables with provenance.

**Non-Goals:**
- Position Training, In-Match Roles, manager tactics (no data), saving a manager in `Build`/`community.saveBuild`, any database or R2 write, any access to efootbase.com, removing the `rating*` columns or the eFHUB cross-fill, reworking the other tabs of the detail page.

## Decisions

**1. A data module for the constants; engine code stays separate.** New `packages/shared/src/ovrModel.ts` holds the weight table (per position name → per term name → integer), the proficiency band table (level → ranges), the three scale factors and a header comment naming the source (efootbase's public client), the owner-accepted terms risk and a pointer to `docs/efootbase-exact-model.md`. It contains integers and stat names only. `progression.ts` imports it. Alternative: embed in `progression.ts` — rejected so that re-deriving the constants after an efootbase update replaces one file. `ovrWeights.ts` loses the fitted weights, `OVR_PROFICIENCY_*` and confidence lists; the file is deleted once nothing imports it (it is part of the replaced model, not an unrelated dead surface).

**2. Pipeline order is fixed and tested.** For stat `s₀` = base + training: `s₁ = s₀ ≥ 99 ? s₀ : min(99, s₀ + band(level, s₀))`; `final = s₁ + Σ active boosters + (manager pill ? 1 : 0)`. Final stats feed the overall; position scaling happens inside the overall (`round(final × f)` clamped 0..255, including defensive engagement and goalkeeper stats, not height or weak foot). Rounding is `floor(x + 0.5)`; the overall is `floor((sum + 499) / 1000)` clamped 40..127. Weak-foot term uses `59 × accuracy / 3 + 40` as a real number before the 25 offset. Reading the survey code is the source of truth where this text and the code differ; tests pin the code. One difference was found and is resolved for the text, not the code: efootbase's client limits the trained stat to 99 unconditionally (`min(99, s₀ + band)`), so a stat trained above 99 (e.g. 98 + 4) would be cut back to 99. No measured reading has `s₀ > 99`, so the survey cannot decide; the population check can — on the 99 cards whose eFHUB max-level stats exceed 99, the formula equals efootbase's max-level overall on 94 when those stats are kept and on 65 when they are cut. The engine keeps them (the text above, and the existing "no clamp at 99" training rule).

**3. Manager as an input to the engine, not a row lookup.** `simulateBuild` receives `proficiencyLevel` and an optional `manager` `{ stats: BaseStat[] }` (one or two stats: 24 of the 69 picker managers have a single pill on efootbase, `booster_2` null — found during implementation; the survey's 12,324/12,324 manager cells were scored with null pills dropped); selecting a manager is a UI action that sets level = rating and passes its pill stats. The engine does not know manager ids. UI state: `managerId | null`; moving the slider calls `setManager(null)`; Reset and Max OVR do not touch it; clicking the selected row sets it to null and leaves the level. Alternative: have the engine derive the level from the manager — rejected so the engine stays a pure function of numbers and the "slider deselects" rule lives in one place (the panel state).

**4. Max OVR objective.** The preset keeps the exact dynamic programme over the ten categories (budget in half-points) with the objective Σ weight × stat for the selected position (linear part of the formula, offsets and scaling ignored), independent of proficiency, as efootbase's preset was on the five measured cards. Acceptance is empirical: the preset's allocation on each fixture card at its registered position, simulated at proficiency 70/80/85/90, must reproduce the recorded Max readings; the reference card must give 106/109/109/110 (Max) and 94/97/97/97 (Reset). If the linear objective picks a different allocation than efootbase on a card, the finding is reported and the objective is not tuned to fit.

**5. Tiles are computed, not stored.** A shared function returns all 13 overalls for a final stat vector, height, weak-foot accuracy and the card's aptitudes. `PlayerDetailClient` calls it with the stats it already renders (projected stats when the panel is open, otherwise the stats shown, including the "stats at max level" toggle), then derives Best Fit, "At XX" and the Pitch Map input; `PitchMap` takes `tiles` instead of `positionRatings`. The compare page calls the same function on each card's displayed stats for its tooltip. The `rating*` columns and `positionRatings` in the DTO stay (cross-fill unchanged, other consumers possible) but nothing displays them.

**6. `manager.picker` is a small public query.** New `apps/api/src/router/routers/manager.ts` registered in `root.ts`: no input, selects `inPicker = true` ordered `rating desc, id asc`, returns `{ id (string), name, rating, imageUrl (rebased with `rebaseR2Url`), pills: stat[] }` with one or two stats (45 rows have `booster2Stat`, 24 do not — as on efootbase), and throws a `TRPCError` (INTERNAL_SERVER_ERROR) if a picker row lacks its first pill or carries a name that is not a base stat, rather than inventing one. The web fetches it when the dialog first opens and keeps it with `staleTime: Infinity`. Alternative: put it in the `player` router — rejected, managers are a separate entity and the old `manager` router was deleted in `remove-dead-surface`.

**7. Dialog with the platform primitives.** The picker is a native `<dialog>` opened with `showModal()` (focus trap, Escape and focus return come from the platform), labelled by its heading, with a search input, a scrollable list of buttons and `aria-pressed` on the selected row. Rows use plain `<img loading="lazy">` like the cards. No dependency is added. Alternative: a headless-UI package — rejected (First Load JS budget, no new dependency).

**8. Oracle fixture is numbers only.** `packages/shared/src/__fixtures__/exact-model-oracle.json` (at most 300 lines, one reading per line) holds, per anonymous card id (`c1`…`c5`): height, weak-foot accuracy, the 13 aptitudes in our coding, registered position index, level cap, base stats, booster vectors, and a sample of readings (level, manager pill stats or none, allocation per category, expected 26 stats, 13 tiles, overall). As built: 273 lines, 262 readings (210 no-manager readings = 5 cards × 2 builds × 21 levels, 52 manager readings: every reading with a pill stat above 99, one per rating, single-pill managers), three allocations per card (A = Reset, C = the survey's second build — efootbase's Max build only on the reference card, hand builds on the other four — and M = efootbase's own Max build from the opening sheet) and `maxOvr`, efootbase's Max OVR overall per level (from the earlier capture's numbers-only fixture for the CB/DMF/CF cards at 21 levels and the reference card at 5 levels, and the goalkeeper's opening reading at 90). No names, ids or text of efootbase. A separate script outside the repository replays all 5 cards × all builds for the report. The old `proficiency-oracle.json` and the fitted-overall tests are replaced because the model they pin is removed; `progression-oracle.json` (hub max stats, budget, cost curve, DP optimality) stays for the rules that do not change.

**9. Tamper tests.** Each change listed in the task (one weight, one band bound, no manager +1, swapped booster/manager order, different rounding, changed scale factor, changed clamp) is applied to a copy of the model in the test and must make an oracle assertion fail. As built (20 cases, all detected): a literal swap of the booster and manager additions is a no-op (both are plain additions after the cap, so the result cannot change); the meaningful order tampers — the manager's +1 applied before the bonus and the 99 cap, and the boosters applied before them — are the ones tested. Lowering the ceiling 127 → 126 changes no fixture reading (none reaches 127), so the ceiling, the floor and the 255 scaled-stat limit are also pinned by direct unit checks (section 5: the 255 check uses one heavily weighted stat at 300 vs 255 vs 200 with the overall below 127, and fails with the limit removed or set to 200 or 120 — mutation-checked).

**10. Honest copy.** Remove "~", anchor and ±1 notes. Add one line under the overall: "Computed with efootbase's formula (matched on N readings); stats and height come from the database dump." Keep a visible note that Position Training and In-Match Roles are not modelled. N is the number of readings in the final verification report, not a literal chosen in advance.

## Risks / Trade-offs

- [Terms risk of constants taken from efootbase's client] → owner accepted; commit integers only, record provenance, keep no code or data files; the verify step scans the diff for long foreign strings.
- [The formula may not equal efootbase for cards outside the five measured] → population check (formula on stats at max level + Booster 1 vs `overall_at_max_level`, 9,839 cards) is reported as measured; the "Level cap 1 card" scenario promises nothing beyond that report; if the match rate is low the limits copy says so.
- [Linear Max OVR objective may not match efootbase's Max on unmeasured cards] → reported, not tuned (Decision 4).
- [Manager order differs from efootbase's source order] → documented; adding an order column needs a migration in a later change.
- [Compare page and detail page diverge if only one is updated] → both use the shared tile function; the smoke or unit test imports it.
- [A 99+ stat with a +1 pill, or a booster pushing a stat above 255 scaling clamp] → covered by the clamp in the formula and a unit test.
- [efootbase changes constants] → `docs/efootbase-exact-model.md` documents the regeneration; tests will fail loudly against the committed fixture, not silently drift.
