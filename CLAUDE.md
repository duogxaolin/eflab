## What this is

**eflab** = "eFootLab" — a fan-made eFootball player database: every card with real stats, side-by-side compare, the latest packs and the full skill list. Turborepo + pnpm monorepo. Not affiliated with Konami; all player data comes from public third-party dumps (efootbase API dump as primary, eFHUB CDN SQLite as secondary cross-fill).

**The GitHub repo `duogxaolin/eflab` is PUBLIC** (`main` is pushed). Never commit secrets, `dump/`, database backups, Konami assets or audit reports. Two third-party keys were committed in `docs/` before 2026-10-17; they are redacted in the working tree but **still exist in git history** — rewriting history and rotating them is the owner's decision (see "Known limitations").

This repo is **distinct from the `bno` bot** (a separate eFootball scraper the user also runs). Data-source decisions for bno live in memory under `bno-bot-data-decision`. **Don't conflate the two** — bno uses pesdb images and efhub data; eflab uses efootbase card renders mirrored to R2.

## Player data pipeline

Player data is **not** self-datamined from the game (see `docs/efootball-apk-datamine-analysis.md`). Source of truth is the **efootbase dump**, with **eFHUB** as a secondary cross-fill.

1. **Dump** — `scripts/efootbase_dump.py` (needs `EFBASE_API_KEY`; the script reads it from the `.env` passed with `--env`, default an APK-extract path) → `dump/efootbase/players.jsonl` (50,691 cards × 176 cols, re-dumped 2026-10-18), `players_meta.json` (field labels, card-type labels), `packs.json` (featured bundles), `teams.json`, `images/` (98,367 card/emblem files, ~6.5 GB). `dump/` is gitignored. See memory `efootbase-datapath`.
2. **Seed** — `pnpm db:seed` (`packages/db/src/seed-efootbase-full.ts`). **Non-destructive upsert in ONE interactive transaction** (60-min timeout): Player and Manager are `INSERT … ON CONFLICT DO UPDATE` over a column list generated from the Prisma model minus `PLAYER_CROSSFILL_COLUMNS` / `MANAGER_CROSSFILL_COLUMNS`, so cross-fill-owned columns are **never written by the seed**. Country/League/Team/Pack/PackCard/Skill/PlayerSkill/FeaturedBundle(+Card) are replaced inside the same transaction (no FK reaches a user table). Booster is upserted by id (dump wins over fixtures). User tables (User/Account/Session) are untouched unless `--reset-users`; players missing from the dump are kept and logged unless `--prune`. The JSONL is streamed twice (lookups, then writes). Field mapping uses the dump's real keys: `jumping→jump`, `set_piece_taking→placeKicking`, `tackling→ballWinning`, `pos→registeredPosition`, `condition` via `[E,D,C,B,A]`, `injury_resistance`, `player_value→marketValue`, `leg_length_height→dribbleHeight`, `name_normalized→nameNormalized`. Unmatched `s_*` skill keys, card-type codes that disagree with `players_meta.json`/pack names, and unknown booster stat keys abort the seed. Position ratings (`ratingGK…ratingCF`) are nullable and left null by the seed.
3. **Cross-fill** — `pnpm db:crossfill` (`packages/db/src/seed-efhub-crossfill.ts`) reads `dump/efhub/efhub_db.sqlite` through the `sqlite3` CLI (`SQLITE3_BIN`, ServBay: `/Applications/ServBay/bin/sqlite3`; `EFHUB_DB_PATH` overrides the file). Writes only what efootbase cannot expose: Manager tactic ratings (exact-id merge, then name merge with `ALIASES`, then create — 1,475 managers, all with tactics, 65 with R2 art), `Player.stars/reputation/overallPotential/gkClearing/maxGkClearing`, the 13 `ratingGK…ratingCF` from eFHUB `overallGK…overallCF`, `communityTier` (10,745 tier badges), and 3 eFHUB-only players (ovr/maxOvr 40 placeholders). `registeredPosition` is seed-owned (dump `pos`); the cross-fill only reports mismatches. All SQL uses bound parameters. Idempotent.
4. **`pnpm db:refresh` = `db:seed` then `db:crossfill`** — the documented refresh. A standalone `db:seed` keeps earlier cross-fill values but cannot add them; it prints that notice.
5. **Verify** — `python3 -I scripts/verify-seed.py` streams the dump and compares it with the DB over read-only psql (`PGOPTIONS=-c default_transaction_read_only=on`); exit 1 on any mismatch.

**Counts after `db:refresh` (2026-10-19, re-dump of 2026-10-18):** Player 50,694 (50,691 dump + 3 eFHUB) · Manager 1,475 (all with tactics) · Booster 379 · Pack 2,065 / PackCard 13,828 · FeaturedBundle 24 / FeaturedBundleCard 166 · Skill 84 (the dump's 67 `s_*` keys cover 67 of them; the other 17 fixture entries have 0 holders) · PlayerSkill 195,607 · Country 185 · Team 736 · League 34 · tier badges 10,745 · newest `releaseDate` 2026-10-15. Card types: STANDARD 36,817 · HIGHLIGHT 8,558 · TRENDING 3,608 · EPIC 1,094 · SELECTION 314 · LEGENDARY 261 · STRIKE_ARENA 42.

**2026-10 re-dump (2026-10-18/19)** — `scripts/efootbase_dump.py` (rewritten: no hard-coded last page, atomic `players.jsonl`, retries, incremental image sync via the CDN ETag) produced 50,691 cards: **2,284 new**, **5,380 changed**, none removed; **9,891 images** were uploaded to R2 (4,568 for the new cards, 5,312 overwritten card images of changed cards, 11 emblems). efootbase API facts: `sort=time_added&order=desc` lists newest first, `limit` ≤ 100, `total_count` / `total_pages` are lookahead values (the end of data is the first short page). Limits: the 2,284 new cards have **no eFHUB cross-fill data** (no stars / reputation / position ratings / tier badge — the local eFHUB SQLite has no rows for them); R2 objects carry a 1-year immutable cache header, so the 5,312 overwritten card images may stay stale in browser / CDN caches until purged or the keys are versioned; `time_added` does not change on stat edits, so changed cards are only found by a full dump + diff.

**Card types** — Prisma/`CARD_TYPES` enum = `STANDARD, LEGENDARY, TRENDING, SELECTION, EPIC, HIGHLIGHT, STRIKE_ARENA`, mapped from efootbase `card_type` codes 0/1/3/4/5/6/7 (`CARD_TYPE_BY_EFOOTBASE_CODE`). Labels come from `CARD_TYPE_LABELS` in `@eflab/shared` (never show raw enum names). "Big Time" and "Show Time" are pack campaigns, not codes: Big Time cards are `EPIC`, Show Time cards are `HIGHLIGHT` (efootbase's own labels). The home quick filter "Epic & Big Time" therefore sends the EPIC scope. **The `/players` default scope is all card types** (no type pre-selected — the live efootbase capture of 2026-10-18 showed that its /players starts with every card type unselected; the earlier "efootbase default = Epic + Highlight" claim was wrong and was corrected in change `efootbase-parity-round2`).

**Homepage "Latest Packs" + `/packs` + `/packs/[slug]` = `FeaturedBundle` table** (24 = 16 `specialPlayerList` + 8 `packs` spotlights from `packs.json` since the 2026-10 re-dump — the split follows efootbase; `FeaturedBundleCard.ordinal` keeps efootbase's display order). Slugs are stable name+date slugs (e.g. `spanish-league-midfielders-2026-10-19`, `spotlight-jurgen-klopp-2026-10-15`); `featured.list` returns them and `featured.bySlug` backs the bundle page. `Pack`/`PackCard` (per-card `featured` field) is a separate historical model that the web no longer routes.

**Search** — `Player.nameNormalized` (dump `name_normalized`, lower-case ASCII) has a trigram GIN index (`gin_trgm_ops`, migration `parity_fixes`). Queries are normalised in TS (`normalizeSearchQuery`: NFD, strip marks, lower-case) and LIKE-escaped (`escapeLike`). `player.list q` = `nameNormalized LIKE '%q%'` (plus `japName`/`chineseName ILIKE` only when the query has non-ASCII — the CJK path is not index-backed); `player.search` tiers exact-substring above trigram similarity (`tier ASC, similarity DESC, ovr DESC`). Minimum 2 characters.

## Conventions

- Match the surrounding code: comment density, naming, idiom. Vietnamese comments are common in this repo (user is Vietnamese) — okay to use Vietnamese for user-facing docs/comments when the surrounding code does.
- Prisma BigInt IDs are serialized via SuperJSON — tRPC procedures receive/send BigInt as strings in JSON but `bigint` at runtime. Ids are validated with `bigIntString` (≤ 19 digits, ≤ int8 max → 400, never 500); integer filters are int4-bounded.
- Card types: `CARD_TYPES` / `CARD_TYPE_LABELS` from `@eflab/shared` (see "Card types" above). Sort fields: `SORT_FIELDS` (every entry has a real column; `[sort, id]` tiebreaker everywhere).
- **Multi-valued filters** (change `multi-select-filters`, 2026-10-18): `player.list` takes `positions[]` (≤ 13, `POSITIONS` values), `nationalityIds[]`, `leagueIds[]`, `clubIds[]` (≤ `MAX_FILTER_IDS` = 50 each, int4). Values inside one list are OR-ed (`IN`, positions through the aptitude rule `pos<POS> IN (0,1)`, leagues through the Team relation), lists are AND-ed with each other and every other filter. The single-value fields `position`, `nationalityId`, `leagueId`, `clubId` still work: the router merges them into the list (`mergeFilterValues`), de-duplicates and re-applies the bound — an over-long list, a merged set above the bound, an out-of-range id or an unknown position is a 400, never a 500. The web URL repeats the parameter (`pos=SS&pos=CF`, `nat=3&nat=14`, `league=…`, `team=…`) in a canonical order (positions in catalogue order, ids ascending, no duplicates — `parsePositionParams` / `parseIntListParams` / `sortPositions` / `sortIds` in `@eflab/shared`), reads the older single value (`pos=CF`, efootbase's index form `pos=12`, `nat=14`) and comma lists, drops invalid members and rewrites the link canonically on the next change. **Nation uses our internal `Country.id`** (efootbase uses ISO-like codes; the data has no code column), so shared Nation links are stable only until the catalogue is re-seeded with different ids. UI: Position = 13 `aria-pressed` toggles; Nation / League / Team = the picker dialogs in multi-select mode ("N selected", removable chips, Done; native `<dialog>` focus trap, Escape and focus return — `Modal.tsx` closes the element before unmount so Done returns focus too); the mobile Filters badge counts each multi-valued filter once. The pickers enforce `MAX_FILTER_IDS` themselves (`PickerList max`): at 50 the unselected options are `aria-disabled` and an "At most 50 selections" live message shows, removals still work, so the serialiser's `slice(0, MAX_FILTER_IDS)` is a safety net that a UI-built state never reaches. `PickerList` owns the list's load state (`load` prop) so "Nothing matches." appears only once the list is loaded. The shared `int4` schema accepts a number or a digit string only (`[null]` is a 400, not id 0). Query cost (read-only `EXPLAIN (ANALYZE)`, 2026-10-18): every measured combination, including the worst case of 13 positions + 50 teams + a stat range, ran well under 100 ms (all below 25 ms; figures in the change's tasks.md) — no new index.
- **Theme = efootbase zinc + lime** (since 2026-10-07 session 3; the earlier "Slate-Emerald" and "Cyber-Sport Dark" palettes are gone). Tokens in the `@theme` block of `apps/web/app/globals.css`: canvas `#060607`, panel `#18181b`, elevated `#232325`, line `#28282c` (active `#3f3f45`, separator `#212124`), accent lime `#acf41a` (foreground `#080d02`), secondary cyan `#06b6d4`, warn amber `#f59e0b`, danger `#ef4444`, text `#fcfcfc` / `#9f9fa9` / `#6b6b73`. Tier colours (single source `--color-tier-*`, five tiers since `efootbase-parity-round2`): 100+ `#ff2fb4` (magenta, trained past 99), 90–99 `#00ffb4`, 80–89 `#96ff00`, 70–79 `#ffbe00`, <70 `#ff3200`; consumers go through `statTier`/`statTierClass`/`statTierBg` in `lib/card-display.ts`. Card-type accents `--color-card-*`. Inter via `next/font/google`. Component classes live in `@layer components` so utilities win. See `openspec/ui-dna.md`.
- Branding is **eFootLab** (own SVG wordmark `EflabWordmark.tsx`, footer build stamp from `NEXT_PUBLIC_GIT_SHA`/`NEXT_PUBLIC_BUILD_UTC` filled by `next.config.ts` from git). No "eFootBase" string or efootbase build id anywhere in `apps/web`.
- API env (`apps/api/src/env.ts`): `NODE_ENV` is set by the package scripts (`dev` = development, `start` = production; unset = treated as production → no stack traces, Secure cookies), `WEB_ORIGIN` (comma-separated CORS allow-list, first entry = OAuth redirect target), `API_PORT` (4000), `API_HOST` (0.0.0.0), `API_ORIGIN`, `R2_PUBLIC_BASE`, `GOOGLE_CLIENT_ID/SECRET`, `OAUTH_STATE_SECRET`. tRPC `maxBatchSize` 10 (web `httpBatchLink maxItems: 10`); expected failures are `TRPCError`s; undecodable cookies are ignored.

## Progression simulator (player-progression-simulator, 2026-10-18)

The detail page's Progression panel (`components/build-simulator/ProgressionPanel.tsx`, state owned by `PlayerDetailClient.tsx`) runs the pure engine in `packages/shared/src/progression.ts` on the client (the server-side `community.simulate` twin was removed in change `remove-dead-surface`). Rules recovered from the eFHUB `player export` table (44,103 cards joined to the efootbase dump by Konami id, read-only analysis outside the repo):

- **Budget** = `levelCap − 1` training points (Max Level input 1..levelCap). Σ cost = levelCap − 1 on all 32,601 hub cards with cap ≥ 2. **Displayed unit = efootbase's whole points = 2 × ours** (`toDisplayPoints`, `POINT_DISPLAY_SCALE`): a level-32 card reads "62/62 pts", the first four stat points of a category cost 1 displayed point each, the next four 2 (efootbase-parity-round2; measured "62/62 pts" at cap 32, "54" at 28, "52" at 27).
- **Opening state** (`defaultProgressionState`, 2026-10-18): the Max-OVR allocation (`bestAllocation`) at the registered position with every usable booster on and **Manager Proficiency 90** — efootbase's sheet opens the same way (both boosters on, its own Max-OVR build; its DP differs from ours only where its proficiency bonus and the 99 cap change the marginal gains, e.g. Cannavaro CB: efootbase Dexterity 4 / Lower Body 4 / Aerial 8 / Defending 14 vs ours Lower Body 4 / Aerial 12 / Defending 12). "Custom build" = any deviation from that state (proficiency 90 counts as the default); Reset zeroes every category and keeps the proficiency, Max OVR restores the optimum. Outfield cards open as before except where Goalkeeper 1's Jump contribution wins the optimum (since `jump-from-gk1`): measured on 1 of 9,357 outfield multi-level cards — Umeda Kaito, CF, `/players/152205/105588818334349`, cap 73, opens with Goalkeeper 1 = 1 instead of Passing = 1 (estimate 89.51 → 89.52, rounded overall unchanged; Jump's weight at CF 0.0538 beats Passing's 0.0459). Consistent with the game, where buying Goalkeeper 1 raises Jump.
- **Ten categories** (`TRAINING_CATEGORIES` / `TRAINING_STATS`): Shooting {finishing, placeKicking, curl}, Passing {lowPass, loftedPass}, Dribbling {dribbling, ballControl, tightPossession}, Dexterity {offensiveAwareness, acceleration, balance}, Lower Body {kickingPower, speed, stamina}, Aerial {heading, physicalContact, jump}, Defending {defensiveAwareness, defensiveEngagement, ballWinning, aggression}, GK1 {gkAwareness, **jump**}, GK2 {gkParrying (hub "GKClearing"), gkReach}, GK3 {gkCatching, gkReflexes}. Each stat point raises every stat of the category by 1; a stat in two categories gets the sum — **Jump rises with Aerial Strength and with Goalkeeper 1** (change `jump-from-gk1`, 2026-10-18); no cap at 99. With that table, hub `MAX<stat> − <stat>` equals the summed category values for all 26 stats on **44,103 / 44,103** cards (0 exceptions; the old Aerial-only rule failed on 3,354: every one of the 3,353 goalkeepers with a cap ≥ 2 plus hub PlayerID 179425, DMF, Aerial 8 + GK1 1 → Jump 67 → 76 — the only outfield card with a Goalkeeper 1 value). Checked against the 2026-10-18 efootbase sheet captures (outside the repo): the displayed Jumping equals base + Aerial + GK1 + boosters on 65/65 builds without a proficiency bonus (p ≤ 76) and is consistent with the bonus on 151/151 builds above it — 216 builds on Čech GK, Cannavaro CB, Neuer GK and Messi SS, 78 of them with Goalkeeper 1 > 0 (the old engine, goalkeeper Jump left at its base: 36/65 and 91/151; the literal Aerial-only rule would give 40/65 and 97/151). The web's stat-row highlight therefore maps a stat to a *list* of categories (`STAT_CATEGORIES` in `components/detail/StatGrid.tsx`; clicking Jumping cycles Aerial Strength → Goalkeeper 1 → clear). **Display labels** = efootbase's (`PROGRESSION_CATEGORY_LABELS` in progression.ts): Shooting, Passing, Dribbling, Dexterity, Lower Body Strength, Aerial Strength, Defending, Goalkeeper 1/2/3 (the short `TRAINING_CATEGORY_LABELS` in constants.ts are no longer rendered).
- **Cost curve**: the nth stat point of a category costs `0.5 × ⌈n/4⌉` points (integers in half-points in code): c(2)=1, c(4)=2, c(8)=6, c(12)=12, c(16)=20, c(20)=30, c(22)=36.
- **Boosters**: resolved `booster1`/`booster2` DTO vectors; every usable booster on at open (efootbase shows both on); unknown ids show "unknown booster", never a guess. A booster with an empty stat vector (Booster 136 "Booster +1" and id 0 — together with an absent Booster 2 that covers 50,617 of the 50,691 dump cards: 1,128 × 136, 45,386 × 0, 4,103 absent) shows "(no stat data)" with no toggle and never counts as a custom build. The stat grid shows booster bumps as cyan "+N" chips (training is inside the value).
- **Manager Proficiency** (change `manager-proficiency-slider`, 2026-10-18; measured on efootbase's sheet, six cards, scripts and captures outside the repo): efootbase applies a "Manager Proficiency" bonus (slider 70–90, default 90) to every stat even with no manager selected; the panel now has the same slider (default 90, `ProgressionState.managerProficiency`, `BuildConfig.managerProficiency`, engine default `MANAGER_PROFICIENCY_DEFAULT` = 90). Rule (`managerProficiencyBonus` / `applyManagerProficiency`): with `s` = base + training (Jump with Aerial + GK1), shown stat = `s + bonus + Booster 1 + Booster 2`, bonus = 0 when `s ≥ 99`, else `min(99 − s, ⌊s × r(level)⌋)`; boosters come after the bonus and may exceed 99. `MANAGER_PROFICIENCY_RATES`: 70–76 → 0; 77 → 0.02116; 78 → 0.02286; 79–80 → 0.02614; 81–82 → 0.02878; 83 → 0.03031; 84–85 → 0.03243; 87 → 0.03419; 88 → 0.0355; 89 → 0.03593; 90 → 0.03625. **Level 86 is an unconfirmed exception**: no single rate fits it (its feasible interval is empty), the bonus is `⌊(s + 6) / 32⌋` (reproduces all 207 measured cells) and the panel flags it when 86 is selected (`BuildResult.managerProficiencyUnconfirmed`). Ambiguous cells (s = 66 at 83, s = 88 at 87) are excluded from the fixture. `BuildResult.proficiencyDeltas` carries the per-stat bonus (stat-row tooltip). At proficiency 70 the **stats** are identical to the engine without the control (61,074/61,074 builds on the 261-card hub oracle, `bestAllocation` identical); the **overall** at the registered position differs by the anchor (the panel passes `cardOvr`: 1,336 of 4,698 registered-position builds round differently from the pre-change engine). **Evidence, kept apart** (scripts outside the repo):
  - *In-sample* (rates pooled over all six cards; the fixture is that same data, so this is a regression guard, not a validation): 6,838/6,838 stat cells, anchored overall within ±1 263/263 (unanchored 218/263).
  - *Held-out* (rates read off Messi SS at 70/75/80/85/90 and Neuer GK at 70/90 only, then frozen; Cannavaro CB, Čech GK, Rodri DMF, Haaland CF predicted at 70/75/80/85/90): 178 builds, 4,628/4,628 stat cells; overall within ±1 142/178 unanchored, 178/178 anchored. The anchor was chosen **post hoc**, after the Čech failures were seen (14/50 → 50/50); Cannavaro, Rodri and Haaland pass with or without it, so the held-out builds do not test the anchor.
  - *Prospective* (rates from Messi, Neuer, Cannavaro, Čech; Rodri + Haaland predicted at all 21 levels, 164 builds): 4,257/4,264 stat cells at the interval midpoints (4,263 at the lower bounds, 4,252 just under the upper), misses at 79/81/82/83; overall within ±1 164/164 anchored and unanchored.
  - *Not covered*: the 15 levels between the held-out ones (71–74, 76–79, 81–84, 87–89) were measured on four cards only (no two-card held-out run); their 100 % fit needs Rodri + Haaland in the pool (the shipped 79/81/82/83 rates are in-sample for them). Level 86's exception was fitted on all six cards. Shipped rates are points inside the measured intervals (widths 0.00022–0.00092); a rate moved inside its interval (r90 = 0.0362, r80 = 0.0262, r83 = 0.0300 were tried) passes every test — undetectable by design.
  - Messi SS, efootbase's Max build (Shooting 8, Passing 4, Dribbling 12, Dexterity 8, Lower Body 7 — also our `bestAllocation`) at 70/80/85/90: measured 106/109/109/110, engine 106/108/109/109; Reset measured 94/97/97/97, engine 93/96/97/97 (anchored exact 4/8, unanchored exact 6/8; all within ±1).
  - Level 86 is also non-monotone: s = 26–29 and s = 58 gain 1 more at 86 than at 87 (unconfirmed, kept as measured).
- **Anchor** (`ovrAnchor`, `SimulateInput.cardOvr`): at the registered position the estimate is `round(formula(shown stats) + anchor)` with anchor = card `ovr` − formula(base stats, no boosters) — it absorbs the per-card residual of the shared weights. Chosen post hoc (see above); its independent support is the **population check** (no bonus involved; formula on hub max stats + Booster 1 vs efootbase `overall_at_max_level`, within ±1 unanchored → anchored): 10,073 cards with dump `max_level` > 1: all 94.7 % → 96.1 %, GK 82.0 % → 95.5 % (716); the 9,839 of them whose hub level cap is also > 1: all 97.0 % → 98.3 %, GK 83.6 % → 97.4 % (702). The denominators differ because 234 cards have hub level cap 1 (hub max = base, so the comparison is meaningless for them). Anchored bias stays −0.33 (GK −0.66). Other positions are **not anchored** (fitted half/none penalty unchanged). Measured on efootbase's position tiles of the six fixture cards (bonus applied, unanchored): full-proficiency off positions within ±1 on 202/202 tiles; half-proficiency tiles read +3.8 above our estimate (3–5, 0/224 within ±1); non-proficient tiles where our estimate is above the floor of 40 read +2.6 (122/2,483 within ±1); where our estimate sits at the floor (goalkeeper card at an outfield position, outfield card at GK) efootbase agrees within ±1 on 1,145/1,231 tiles (1,098 exactly 40). The panel's warning says exactly that ("Not anchored" at full positions and at the floor, "Not confirmed: efootbase tends to show about 4 / about 2–3 higher" at half / none above the floor) and labels the 99.9 % / 99.7 % penalty figures as hub figures.
- **Max Level input**: a draft string while typing; committed and clamped to 1..levelCap on blur / Enter (spinner and arrow keys commit at once); an invalid or empty draft reverts; the allocation is reset only when the committed level can no longer afford the points spent, and the live region announces it.
- **Estimated overall** (`~`): per-position linear weights in `ovrWeights.ts` fitted on the hub's `overall<pos>` of cards with **full proficiency** at that position (held-out R² 0.992–0.999; within ±1 for ≥ 99.9% of cards at 11 outfield positions, 98.6% CB, 93.3% GK). Cross-check: formula(hub max stats + Booster 1) is within ±1 of efootbase `overall_at_max_level` for 94.7% of the 10,073 cards with progression — and since `jump-from-gk1` the engine's projection (hub base stats + allocation) equals the hub max stats on every card, so the same 94.7% holds for the engine fed with hub base stats (the web feeds the dump's base stats, which differ from the hub's on 3,849 of the 44,082 joined cards — Jump on 1 — so its figures can deviate slightly) (GK 82.0% = 587/716, up from 36.0% while goalkeeper Jump was left at its base value; 11 outfield 95.9%, CB 96.1%, CF 94.7% unchanged; fixture GK 18/20, was 6/20 — no refit needed). The hub's own `MAXOverall<pos>` sits about +3.6 above the formula (+4 on 47% of cards, +3 on 44% — hub quirk, not applied).
- **Proficiency penalty** (`OVR_PROFICIENCY_ADJUST`, 2026-10-18): the ±1 claim only holds at full-proficiency positions — unpenalised, the formula is within ±1 of the hub on 0% of half-proficiency and 5.6% of non-proficient observations (mean +6.3 / +13.8 too high). The hub overall at a half / non-proficient position is `max(40, k·estimate + c)` with per-position `k, c` (half ≈ 0.93·est − 1.6, none ≈ 0.82·est − 5.9; GK at none = flat 40). Held-out within ±1: half 99.9% (21,387 obs; CB 98.5%, CF 98.9%), none 99.7% at outfield positions (111,819 obs; CB 97.3%, CF 99.7%), GK-none 100%. `simulateBuild` takes the card's `positionAptitudes` (0 full / 1 half / 2 none) and reports `BuildResult.proficiency`; the panel labels every position option with its proficiency and swaps the accuracy note.
- **Max OVR** = exact DP over the categories (budget in half-points, linear objective — the proficiency bonus is left out of it on purpose, so the preset is the same at every proficiency level, exactly like efootbase's own Max OVR build, which was one allocation per card across all 21 levels on 5/5 measured cards); Reset zeroes the categories and keeps the proficiency. Decided in the verify round of `manager-proficiency-slider`: a bonus-aware exact optimum (grouped knapsack, Aerial + GK1 joint for Jump) was measured and rejected — it moves Messi off efootbase's 8/4/12/8/7 at 80/85/90 and does not improve the Max readings (89/89 within ±1 either way). Cost of the linear preset, tested in section 8 of progression.test.ts on 261 hub-oracle cards × 21 levels at the registered position (both boosters, anchor): the bonus-aware optimum is higher on 1,694/5,481 pairs, by at most 0.668 unrounded and 1 displayed point (202 pairs), never at 70–76; the panel says a hand-made build can read up to 1 higher. With the bonus and the anchor the DP build lands within ±1 of efootbase's own Max OVR reading on 89/89 fixture readings, although the allocation itself differs on 4 of the 5 cards with a recorded Max build.
- **Hidden** for `levelCap ≤ 1` cards (40,516 of the 50,691 dump cards) — the note "Progression and manager data are not available for this card…" replaces the panel (efootbase keeps a "Build" card with a manager picker there; we have no manager data). The stat grid has a three-way view: **Build (~N)** (engine projection, the default whenever a panel exists), **Max (N)** (dump `max_attributes`, a different lift) and **Base (N)**; any change in the panel switches back to Build, so the two "max" meanings never mix (decided + tested in efootbase-parity-round2; the old "toggle disabled while custom" rule is gone).
- **Card face** prints the live build estimate in the OVR block (efootbase does the same) with a small "~N EST" tag; the MAX badge and the single header pill are the dump's max overall (Booster 1 only, no proficiency bonus — so it sits below the opening estimate, e.g. Messi 105 vs ~109); a visible "dump max · no proficiency bonus" label sits next to the pill (`ovr-pill-note`).
- **Not modelled**: per-manager effects (no dataset ties a manager to a stat), exact overall values, efootbase's Position Training toggle and In-Match Roles (no data in the dump). (Goalkeeper Jump is no longer a gap: it follows Aerial Strength + Goalkeeper 1 like every other stat.)
- **Regeneration**: weights + proficiency table + fixture come from scratch scripts outside the repo (hub SQLite joined to `players.jsonl`); replace `ovrWeights.ts` (both tables) and `__fixtures__/progression-oracle.json` (cards carry `alt` = hub overall at every non-full position) together when the game version changes. The Manager Proficiency rates and `__fixtures__/proficiency-oracle.json` (6 cards, 263 builds, 6,838 stat cells, numbers only, 280 lines) come from efootbase sheet captures; the tests re-derive each level's feasible rate interval from the fixture and fail if a shipped rate falls outside it, if a displayed stat is missed, or if the anchored overall drops below 95 % within ±1 (goalkeepers asserted separately) — in-sample guards, not validation; section 8 bounds the linear Max OVR preset against an exact bonus-aware optimum (< 1 unrounded, ≤ 1 displayed, equal at 70–76). `pnpm --filter @eflab/shared test` re-checks the stat map (all 26 stats on all 261 fixture cards, goalkeepers and the 179425 case included — Jump = Aerial + GK1), cost curve, budget invariant, ±1 accuracy (aggregate + per-position floors CB ≥ 85%, CF ≥ 95%, GK ≥ 90% at level 1, GK ≥ 75% at max level; half/none ≥ 99%, GK-none = 40) and DP optimality (against an independent top-down knapsack on every fixture card and on 13 positions × budgets 0–40) on the fixture.

## Known limitations (reported, not hidden)

- **Progression is an estimate** — the overall formula is fitted (±1 at full-proficiency positions, lower confidence for GK/CB; half / non-proficient positions use a fitted penalty, within ±1 on 99.9% / 99.7% of held-out hub observations — hub figures; efootbase reads higher there), weights track the hub's game version; builds are not persisted anywhere (the Build table and `community.saveBuild` were removed).
- **Manager Proficiency limits** — the stat rule is held-out-tested only at 70/75/80/85/90 (the 15 levels in between rest on four cards; level 86 is a fitted, unconfirmed and non-monotone exception); the anchor was chosen post hoc (independent support: the population check); the overall is anchored only at the registered position — at half / non-proficient positions efootbase reads about 4 / 2–3 higher than our estimate unless it sits at the floor of 40 (warned in the panel); the Max OVR preset ignores the bonus (up to 1 displayed point below the bonus-aware best); no per-manager effects (no manager picker, no dataset).
- **Dump freshness** — re-dumped 2026-10-18 (see "2026-10 re-dump" above); the newest `releaseDate` in the DB is 2026-10-15 (was 2026-10-01 with the 2026-10-06 dump; Ricardo Quaresma, base 4526, missing then, is now present). The 2,284 new cards have no eFHUB cross-fill data, overwritten R2 card images may be served stale from caches (1-year immutable), and `time_added` does not move on stat edits. Refreshing again needs `scripts/efootbase_dump.py` + `EFBASE_API_KEY`.
- **efootbase could not be compared on results** — its API sits behind a Cloudflare bot check, so the /players filters, sort presets and search were verified against our own data only; labels and controls follow the 2026-10-18 capture.
- **Position Training / In-Match Roles** — efootbase has them, the dump has no such data; not built.
- **Body Model, Form, Injury Resistance** — stored for every card (`Player.neckLength…legLength`, `legCoverage…dribbleHeight`, `form`, `injuryResistance`; form/injury are 0–2 and efootbase shows value + 1 stars of 3). `player.byId` / `player.compare` (`toCardDTO`) return them as `PlayerCardDTO.physique` (11 ints), `bodyMetrics` (5 floats), `form` and `injuryResistance`; the detail page renders the real values (no migration — the columns were already seeded). The fields are typed optional in the DTO so a caller without them (none today) degrades to the "not exposed" note instead of a placeholder number.
- **Skill labels are display-only** — `apps/web/lib/skill-labels.ts` maps stored names to efootbase's observed labels and Showtime/Classic groups; the database keeps the fixture names.
- **Post-dump skills and playing styles** — efootbase's Skills filter (2026-10-18 capture) lists 28 Showtime skills; 5 of them (Beast Drive, Decisive Pass, GK Aerial Claim, GK Rush Out, Sharp Cut) do not exist in the dump or the 84-row `Skill` table, so our Showtime group has 23 and no card can be filtered by them. The AI style "Long Ranger" has no column. The 4 playing styles that post-dated the first dump arrived with the 2026-10 re-dump and are mapped since 2026-10-19 — Press Back 23, Tough Marker 31, Deep Defender 32 (defence slot), Build-up GK 34 (attack slot), named from efootbase's English UI strings because `players_meta.json` still has no label for them; `PLAYING_STYLES_UNAVAILABLE` is empty (the disabled-pill mechanism stays for future styles).
- **40,516 cards have `levelCap` 1** — that is what the dump carries (37,217 of them also have `maxOvr == ovr`; 50,691-card dump of 2026-10-18), not a seeder bug.
- **CJK search** (`japName`/`chineseName ILIKE`) runs only for non-ASCII queries and is not index-backed.
- **Nation filter links carry internal ids** (`nat=14`), not ISO codes — `Country` has no code column; a re-seed that renumbers countries changes what an old link means (see "Multi-valued filters" under Conventions).
- **Kept on purpose after `remove-dead-surface` (2026-10-18)** — not dead by accident, each has an owner decision behind it: the `auth` router + Google OAuth + User/Session/Account (no sign-in UI is routed; `auth.tsx` still calls `getSession`/`signOut`); `protectedProcedure` in `router/trpc.ts` (no mounted procedure uses it since the community routers went); the Pack/PackCard (2,065 / 13,828) and Manager (1,475) tables with their seeding and cross-fill (data assets, no API reads them except `player.byId` → Pack name); `better-auth` (only `better-auth/crypto` is imported); `zod` and `superjson` as direct `apps/api` dependencies (the API imports both through `@eflab/shared`). The R2 bucket still holds the `card-backgrounds/`, `frames/`, `managers/` objects nobody renders.
- **Konami fonts** (`apps/web/public/fonts/eFootballSans-*.ttf`, `eFootballStencil-Regular.ttf`, loaded by `globals.css`) have an unknown licence.
- **Git history still contains the two previously committed third-party keys** (`docs/apk-db-expansion.md`, `docs/efootbase-ui-dna.md`); redaction covers the working tree only.
- **No CI** — `pnpm typecheck` and `pnpm test` are run by hand.
