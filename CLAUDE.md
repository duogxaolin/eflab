## What this is

**eflab** = "eFootLab" — a fan-made eFootball player database: every card with real stats, side-by-side compare, the latest packs and the full skill list. Turborepo + pnpm monorepo. Not affiliated with Konami; all player data comes from public third-party dumps (efootbase API dump as primary, eFHUB CDN SQLite as secondary cross-fill).

**The GitHub repo `duogxaolin/eflab` is PUBLIC** (`main` is pushed). Never commit secrets, `dump/`, database backups, Konami assets or audit reports. Two third-party keys were committed in `docs/` before 2026-10-17; they are redacted in the working tree but **still exist in git history** — rewriting history and rotating them is the owner's decision (see "Known limitations").

This repo is **distinct from the `bno` bot** (a separate eFootball scraper the user also runs). Data-source decisions for bno live in memory under `bno-bot-data-decision`. **Don't conflate the two** — bno uses pesdb images and efhub data; eflab uses the card renders the efootbase dump links to, mirrored to R2 — mostly efootbase's CDN, but the dump's `transparent` render is a pesdb.net image for 36,815 of 50,691 cards (the sync worker fetches those from `pesdb.net/assets/img/` only).

## Player data pipeline

Player data is **not** self-datamined from the game (see `docs/efootball-apk-datamine-analysis.md`). Source of truth is the **efootbase dump**, with **eFHUB** as a secondary cross-fill.

1. **Dump** — `scripts/efootbase_dump.py` (needs `EFBASE_API_KEY`; the script reads it from the `.env` passed with `--env`, default an APK-extract path) → `dump/efootbase/players.jsonl` (50,691 cards × 176 cols, re-dumped 2026-10-18), `players_meta.json` (field labels, card-type labels), `packs.json` (featured bundles), `teams.json`, `images/` (98,367 card/emblem files, ~6.5 GB). `dump/` is gitignored. See memory `efootbase-datapath`.
2. **Seed** — `pnpm db:seed` (`packages/db/src/seed-efootbase-full.ts`). **Non-destructive upsert in ONE interactive transaction** (60-min timeout): Player and Manager are `INSERT … ON CONFLICT DO UPDATE` over a column list generated from the Prisma model minus `PLAYER_CROSSFILL_COLUMNS` / `MANAGER_CROSSFILL_COLUMNS`, so cross-fill-owned columns are **never written by the seed**. Country/League/Team/Pack/PackCard/Skill/PlayerSkill/FeaturedBundle(+Card) are replaced inside the same transaction (no FK reaches a user table). Booster is upserted by id (dump wins over fixtures). User tables (User/Account/Session) are untouched unless `--reset-users`; players missing from the dump are kept and logged unless `--prune`. The JSONL is streamed twice (lookups, then writes). Field mapping uses the dump's real keys: `jumping→jump`, `set_piece_taking→placeKicking`, `tackling→ballWinning`, `pos→registeredPosition`, `condition` via `[E,D,C,B,A]`, `injury_resistance`, `player_value→marketValue`, `leg_length_height→dribbleHeight`, `name_normalized→nameNormalized`. Unmatched `s_*` skill keys, card-type codes that disagree with `players_meta.json`/pack names, and unknown booster stat keys abort the seed. Position ratings (`ratingGK…ratingCF`) are nullable and left null by the seed. The row mapping and the column-list upsert live in `efootbase-map.ts` / `upsert.ts`, shared with the sync worker (moved unchanged in change `admin-sync-worker`; the seed's output was proven identical on two scratch copies of the live database).
3. **Cross-fill** — `pnpm db:crossfill` (`packages/db/src/seed-efhub-crossfill.ts`) reads `dump/efhub/efhub_db.sqlite` through the `sqlite3` CLI (`SQLITE3_BIN`, ServBay: `/Applications/ServBay/bin/sqlite3`; `EFHUB_DB_PATH` overrides the file). Writes only what efootbase cannot expose: Manager tactic ratings (exact-id merge, then name merge with `ALIASES` — skipped when the name's best eFHUB entry is another Manager row's card, so a new card never copies another card's tactics — then create; 1,475 managers with tactics), `Player.stars/reputation/overallPotential/gkClearing/maxGkClearing`, the 13 `ratingGK…ratingCF` from eFHUB `overallGK…overallCF` (reference only — the web computes position values with the exact formula), `communityTier` (10,745 tier badges), and 3 eFHUB-only players (ovr/maxOvr 40 placeholders). `registeredPosition` is seed-owned (dump `pos`); the cross-fill only reports mismatches. All SQL uses bound parameters. Idempotent.
4. **`pnpm db:refresh` = `db:seed` then `db:crossfill`** — the documented refresh. A standalone `db:seed` keeps earlier cross-fill values but cannot add them; it prints that notice.
5. **Verify** — `python3 -I scripts/verify-seed.py` streams the dump and compares it with the DB over read-only psql (`PGOPTIONS=-c default_transaction_read_only=on`); exit 1 on any mismatch. It also checks the static snapshot (below) when `dump/efootbase/static/` exists. Its manager-duplicate check reads the eFHUB SQLite read-only (`--efhub-db`, default `EFHUB_DB_PATH` / `dump/efhub/efhub_db.sqlite`) to tell cross-fill work still pending after a seed (info) from real duplicates (failure); run it with `--after-crossfill` right after `pnpm db:refresh` so pending rows fail too.
6. **Static efootbase snapshot** (change `efootbase-static-data`, 2026-10-19; `docs/efootbase-static-snapshot.md`) — optional, git-ignored `dump/efootbase/static/skills.json` (72 skills: description, group, wiki order, stat boosts, activation, icon file) and `managers.json` (69 picker managers), taken by hand with a browser survey of efootbase (fragile, no automation). The seed validates both **before** its transaction (unknown stat / unmapped skill / manager that disagrees with the fixture → abort, DB unchanged; missing file → `⚠` warning, seed continues) and then: keeps the fixture slug as the join key; writes efootbase's `name`, `description`, `group` (`SkillGroup` enum SHOWTIME/CLASSIC), `sortOrder`, `efbKey`, `iconKey` (`skills/Skill_<Name>.webp`), `effects` (`[{stat, value}]`) and `activation`; stores the 5 unreleased skills (fixture ids 85–89, `released: false`, hidden by the API); leaves the 17 non-skill entries without a group; sets `Manager.inPicker` for exactly the snapshot ids (69) via a separate UPDATE (`inPicker` is not in the upsert). Stat names in boosts (camelCase) and manager pills (snake_case) go through **one** table, `EFOOTBASE_STAT_MAP` in `@eflab/shared` (`tackling→ballWinning`, `jumping`/`jump`, `set_piece_taking`/`setPieceTaking→placeKicking`, …); `Manager.booster1Stat/booster2Stat` therefore hold eFootLab stat names — for the 65 managers that existed before, the 2026-10-19 seed rewrote them from the fixture's raw snake_case (`lofted_pass`) to camelCase (`loftedPass`); nothing reads these two columns today. R2: 67 icons at `skills/Skill_<Name>.webp` (game stills in two sizes, measured: 58 at 576×346 and 9 at 576×324; `SkillIcon` draws every one uncropped in a 576:346 box with `object-fit: contain`) and the 4 new managers' art at `managers/{id}.webp` (256×256; the 65 older 496×496 images were kept), uploaded with `scripts/r2_upload.py` from a staging folder (never upload the `_manifest.json` files), 71/71 HEAD 200.

## Image pipeline (eflab web)

Cards render **one pre-composited image** from Cloudflare R2: `PlayerCard.tsx` loads `cards/{id}_dynamic.webp` (bg + art + frame baked in) and adds HTML overlays — `.pcb__ovr-block` (OVR + position), `.pcb__condition` (`conditions/condition_{a-e}.svg`) and, with `showDetails`, the nationality flag circle plus MAX LEVEL / MAX OVR badges. The home search dropdown thumbnails use `cards/{id}_transparent.webp`. The 4-layer composite helpers (`cardBgUrl`/`cardFrameUrl`), the manager/emblem key helpers and `lib/efhub-images.ts` (efimg.com fallback) were deleted in change `remove-dead-surface` (the `card-backgrounds/`, `frames/`, `managers/` objects remain in the bucket, unused). CSS 3D tilt + glare stay (disabled under `prefers-reduced-motion`); Three.js/WebGL is rejected. Skill artwork (`skills/Skill_<Name>.webp`, 576×346) is rendered by `components/skills/SkillIcon.tsx` from `SkillDTO.iconUrl` (the API builds it from `Skill.iconKey` with `r2ObjectUrl`, rebased onto `R2_PUBLIC_BASE`): a banner on the `/skills` cards, a 288-px-wide image on `/skills/[slug]`, a 28×17 thumbnail on the player-page chips — raw `<img>`, lazy, explicit width/height.

- **Helper**: `apps/web/lib/r2-images.ts` — `r2Url(key)`, `playerCardDynamicUrl(id)` (used by PlayerCard), `playerCardUrl(id)` (`_transparent`, home thumbnails), `conditionUrl(letter)`. Base URL = `NEXT_PUBLIC_R2_PUBLIC_BASE`, falling back to the dev bucket URL in code.
- **Card image cache version (`?v=`)**: R2 serves objects with `Cache-Control: public, max-age=31536000, immutable`, and a re-dump overwrites changed card images under the same key (2026-10-18: 5,312 overwritten + 2,284 new). `playerCardUrl`/`playerCardDynamicUrl` therefore append `?v=${IMAGE_VERSION}` (R2 ignores the query; browser/edge cache keys change). `IMAGE_VERSION` = `NEXT_PUBLIC_IMAGE_VERSION` (build-time) when non-empty, else the committed `DEFAULT_IMAGE_VERSION` (`"20261019"`). **Bump it whenever card objects are overwritten in place on R2** (after `r2_upload.py` replaced existing `cards/` keys): edit `DEFAULT_IMAGE_VERSION` in `r2-images.ts` (preferred — works without configuration) or set `NEXT_PUBLIC_IMAGE_VERSION` and rebuild the web app. Condition/flag/emblem URLs are not versioned. Every card `<img>` must go through these helpers — never hand-build a `cards/…webp` URL.
- **R2 bucket**: `efootlab`, public dev URL `https://pub-1a19c30950c04ef3964669ac4792f6f0.r2.dev`. Credentials (`R2_ACCOUNT_ID/R2_ACCESS_KEY_ID/R2_SECRET_ACCESS_KEY/R2_BUCKET`) live in the gitignored root `.env` (or, for a strict split, only in the sync worker's service environment — `docs/admin-sync.md`); only `scripts/r2_upload.py` uses them, run by hand or as the sync worker's upload child.

## Conventions

- Match the surrounding code: comment density, naming, idiom. Vietnamese comments are common in this repo (user is Vietnamese) — okay to use Vietnamese for user-facing docs/comments when the surrounding code does.
- Prisma BigInt IDs are serialized via SuperJSON — tRPC procedures receive/send BigInt as strings in JSON but `bigint` at runtime. Ids are validated with `bigIntString` (≤ 19 digits, ≤ int8 max → 400, never 500); integer filters are int4-bounded.
- Card types: `CARD_TYPES` / `CARD_TYPE_LABELS` from `@eflab/shared` (see "Card types" above). Sort fields: `SORT_FIELDS` (every entry has a real column; `[sort, id]` tiebreaker everywhere).
- **Multi-valued filters** (change `multi-select-filters`, 2026-10-18): `player.list` takes `positions[]` (≤ 13, `POSITIONS` values), `nationalityIds[]`, `leagueIds[]`, `clubIds[]` (≤ `MAX_FILTER_IDS` = 50 each, int4). Values inside one list are OR-ed (`IN`, positions through the aptitude rule `pos<POS> IN (0,1)`, leagues through the Team relation), lists are AND-ed with each other and every other filter. The single-value fields `position`, `nationalityId`, `leagueId`, `clubId` still work: the router merges them into the list (`mergeFilterValues`), de-duplicates and re-applies the bound — an over-long list, a merged set above the bound, an out-of-range id or an unknown position is a 400, never a 500. The web URL repeats the parameter (`pos=SS&pos=CF`, `nat=3&nat=14`, `league=…`, `team=…`) in a canonical order (positions in catalogue order, ids ascending, no duplicates — `parsePositionParams` / `parseIntListParams` / `sortPositions` / `sortIds` in `@eflab/shared`), reads the older single value (`pos=CF`, efootbase's index form `pos=12`, `nat=14`) and comma lists, drops invalid members and rewrites the link canonically on the next change. **Nation uses our internal `Country.id`** (efootbase uses ISO-like codes; the data has no code column), so shared Nation links are stable only until the catalogue is re-seeded with different ids. UI: Position = 13 `aria-pressed` toggles; Nation / League / Team = the picker dialogs in multi-select mode ("N selected", removable chips, Done; native `<dialog>` focus trap, Escape and focus return — `Modal.tsx` closes the element before unmount so Done returns focus too); the mobile Filters badge counts each multi-valued filter once. The pickers enforce `MAX_FILTER_IDS` themselves (`PickerList max`): at 50 the unselected options are `aria-disabled` and an "At most 50 selections" live message shows, removals still work, so the serialiser's `slice(0, MAX_FILTER_IDS)` is a safety net that a UI-built state never reaches. `PickerList` owns the list's load state (`load` prop) so "Nothing matches." appears only once the list is loaded. The shared `int4` schema accepts a number or a digit string only (`[null]` is a 400, not id 0). Query cost (read-only `EXPLAIN (ANALYZE)`, 2026-10-18): every measured combination, including the worst case of 13 positions + 50 teams + a stat range, ran well under 100 ms (all below 25 ms; figures in the change's tasks.md) — no new index.
- **Theme = efootbase zinc + lime** (since 2026-10-07 session 3; the earlier "Slate-Emerald" and "Cyber-Sport Dark" palettes are gone). Tokens in the `@theme` block of `apps/web/app/globals.css`: canvas `#060607`, panel `#18181b`, elevated `#232325`, line `#28282c` (active `#3f3f45`, separator `#212124`), accent lime `#acf41a` (foreground `#080d02`), secondary cyan `#06b6d4`, warn amber `#f59e0b`, danger `#ef4444`, text `#fcfcfc` / `#9f9fa9` / `#6b6b73`. ## Progression simulator (player-progression-simulator 2026-10-18; exact model + managers since efootbase-exact-model-managers 2026-10-19)

The detail page's Progression panel (`components/build-simulator/ProgressionPanel.tsx` + `ManagerPicker.tsx`, state owned by `PlayerDetailClient.tsx`) runs the pure engine in `packages/shared/src/progression.ts` on the client (the server-side `community.simulate` twin was removed in change `remove-dead-surface`). Training rules (budget, categories, cost curve) were recovered from the eFHUB `player export` table (44,103 cards joined to the efootbase dump by Konami id, read-only analysis outside the repo); the Manager Proficiency bands, the manager effect and the overall formula are **efootbase's own** constants (`packages/shared/src/ovrModel.ts`, recovered from efootbase's public client during a browser survey kept outside the repo — owner-accepted terms risk; provenance, verification and regeneration in `docs/efootbase-exact-model.md`):

- **Budget** = `levelCap − 1` training points (Max Level input 1..levelCap). Σ cost = levelCap − 1 on all 32,601 hub cards with cap ≥ 2. **Displayed unit = efootbase's whole points = 2 × ours** (`toDisplayPoints`, `POINT_DISPLAY_SCALE`): a level-32 card reads "62/62 pts", the first four stat points of a category cost 1 displayed point each, the next four 2 (efootbase-parity-round2; measured "62/62 pts" at cap 32, "54" at 28, "52" at 27).
- **Opening state** (`defaultProgressionState`): the Max-OVR allocation (`bestAllocation`) at the registered position with every usable booster on, **Manager Proficiency 90** and **no manager** — efootbase's sheet opens the same way. With the exact weights the preset equals efootbase's own Max build on Messi SS, Neuer GK, Cannavaro CB and Rodri DMF; it differs on Haaland CF (fixture card c5; efootbase's build has a lower objective value, 133,336 vs 133,360) and Čech GK (earlier capture only, not in the fixture; a Goalkeeper 2 / Goalkeeper 3 tie, 399 per point each) — fixture 4/5 equal, six distinct cards 4/6 — with the same overall at every level read (69/69 fixture, 89/89 earlier capture). "Custom build" = any deviation from that state (a selected manager included); Reset zeroes every category and keeps the proficiency and the manager, Max OVR restores the optimum and keeps the manager. The DP may buy Goalkeeper 1 for an outfield card when Jump's weight wins the last point (5 of the 241 outfield cards of `progression-oracle.json`; efootbase marks Goalkeeper 1–3 as goalkeeper categories — reported, not changed).
- **Ten categories** (`TRAINING_CATEGORIES` / `TRAINING_STATS`): Shooting {finishing, placeKicking, curl}, Passing {lowPass, loftedPass}, Dribbling {dribbling, ballControl, tightPossession}, Dexterity {offensiveAwareness, acceleration, balance}, Lower Body {kickingPower, speed, stamina}, Aerial {heading, physicalContact, jump}, Defending {defensiveAwareness, defensiveEngagement, ballWinning, aggression}, GK1 {gkAwareness, **jump**}, GK2 {gkParrying (hub "GKClearing"), gkReach}, GK3 {gkCatching, gkReflexes}. Each stat point raises every stat of the category by 1; a stat in two categories gets the sum — **Jump rises with Aerial Strength and with Goalkeeper 1** (change `jump-from-gk1`, 2026-10-18); base + training (+ bonus) is limited to 99 before the boosters (see Manager Proficiency). With that table, hub `MAX<stat> − <stat>` equals the summed category values for all 26 stats on **44,103 / 44,103** cards (0 exceptions; the old Aerial-only rule failed on 3,354: every one of the 3,353 goalkeepers with a cap ≥ 2 plus hub PlayerID 179425, DMF, Aerial 8 + GK1 1 → Jump 67 → 76 — the only outfield card with a Goalkeeper 1 value). Checked against the 2026-10-18 efootbase sheet captures (outside the repo): the displayed Jumping equals base + Aerial + GK1 + boosters on 65/65 builds without a proficiency bonus (p ≤ 76) and is consistent with the bonus on 151/151 builds above it — 216 builds on Čech GK, Cannavaro CB, Neuer GK and Messi SS, 78 of them with Goalkeeper 1 > 0 (the old engine, goalkeeper Jump left at its base: 36/65 and 91/151; the literal Aerial-only rule would give 40/65 and 97/151). The web's stat-row highlight therefore maps a stat to a *list* of categories (`STAT_CATEGORIES` in `components/detail/StatGrid.tsx`; clicking Jumping cycles Aerial Strength → Goalkeeper 1 → clear). **Display labels** = efootbase's (`PROGRESSION_CATEGORY_LABELS` in progression.ts): Shooting, Passing, Dribbling, Dexterity, Lower Body Strength, Aerial Strength, Defending, Goalkeeper 1/2/3 (the short `TRAINING_CATEGORY_LABELS` in constants.ts are no longer rendered).
- **Cost curve**: the nth stat point of a category costs `0.5 × ⌈n/4⌉` points (integers in half-points in code): c(2)=1, c(4)=2, c(8)=6, c(12)=12, c(16)=20, c(20)=30, c(22)=36.
- **Boosters**: resolved `booster1`/`booster2` DTO vectors; every usable booster on at open (efootbase shows both on); unknown ids show "unknown booster", never a guess. A booster with an empty stat vector (Booster 136 "Booster +1" and id 0 — together with an absent Booster 2 that covers 50,617 of the 50,691 dump cards: 1,128 × 136, 45,386 × 0, 4,103 absent) shows "(no stat data)" with no toggle and never counts as a custom build. The stat grid shows booster bumps as cyan "+N" chips and the selected manager's bumps as lime "+1" chips (training and the proficiency bonus are inside the value; a stat row's tooltip splits it into base, training, the cut at 99, proficiency, booster and manager parts).
- **Manager Proficiency** (slider 70–90, default 90 — efootbase applies it even with no manager selected; `ProgressionState.managerProficiency`, `BuildConfig.managerProficiency`, `MANAGER_PROFICIENCY_DEFAULT` = 90). Rule (`managerProficiencyBonus` / `applyManagerProficiency`, efootbase's band table `PROFICIENCY_BANDS`): with `s₀` = base + training (Jump with Aerial + GK1), `s₁ = min(99, s₀ + band(level, s₀))` for every `s₀` — efootbase's client — so a stat trained past 99 reads 99 before the boosters (98 + 4 → 99; `cutTrainedStats`, `BuildResult.capDeltas` ≤ 0, shown in the stat tooltip; `trainingDeltas` keep the raw points); the bonus is 1–3 by range (level 90: 40–55 → 1, 56–82 → 2, 83–98 → 3; level 86 is an ordinary level: 40–57 / 58–89 / 90–98), 0 below the first band, at 99+ and at 70–76. Shown stat = `s₁ + Booster 1 + Booster 2 + manager +1` (only boosters and the manager's +1 pass 99). **Cut at 99 = owner decision (2026-10-19)**, matching efootbase's sheet; until then the engine kept such stats. No survey reading trains a stat past 99 (highest exactly 99), so synthetic unit tests pin it; the game's own max-level overall agrees better with keeping (94 vs 65 of the 99 population cards with such an eFHUB max stat) — recorded in `docs/efootbase-exact-model.md`, not panel copy. Effect: the opening Max OVR build trains a stat past 99 on 108 of the 10,175 dump cards with progression (excess ≤ 10); its overall drops by 1 on 26 of them at proficiency 90 (42 at 70; over all 21 levels −1 on 680 and −2 on 4 of 2,268 card × level pairs). The fitted rates, the level-86 exception and the anchor are gone.
- **Managers** (`manager.picker`, `ManagerPicker.tsx`): "Select Manager" opens a native `<dialog>` (the shared `filters/Modal.tsx`: named, focus trap, Escape, focus return) listing the 69 picker managers (rating DESC, id ASC — efootbase's own order inside a rating is not stored), with art, rating badge and one or two "+1" pills (24 managers have one pill), searchable by name or stat label (accent-insensitive). The list is fetched on the first open (`staleTime: Infinity`).
- **Verification** (scripts outside the repo, `docs/efootbase-exact-model.md`): survey replay of five cards through the shared engine — 793/793 overalls, 20,618/20,618 stats, 10,309/10,309 position tiles, 474 manager readings (12,324/12,324 cells, level = rating 474/474), 98 slider-after-manager readings (deselected on all); the earlier capture's 263 builds (six cards, a second GK; not used to derive anything) 263/263 overalls, 6,838/6,838 stats, Max preset = efootbase's Max reading 89/89. Messi SS Max 106/109/109/110 and Reset 94/97/97/97 at 70/80/85/90 — exact.
- **Max Level input**: a draft string while typing; committed and clamped to 1..levelCap on blur / Enter (spinner and arrow keys commit at once); an invalid or empty draft reverts; the allocation is reset only when the committed level can no longer afford the points spent, and the live region announces it.
- **Overall** (`exactOvr`, no "~"): efootbase's integer formula — every final stat scaled by 1 / 0.97 / 0.85 at a full / half / non-proficient position (`floor(x + 0.5)`, 0..255, defensive engagement and GK stats included), each stat term `max(0, v − 25)`, height `max(0, h − 111 − 25)`, weak foot `59 × a / 3 + 40 − 25`, overall `floor((Σ w·term + 499) / 1000)` limited to 40..127, 13 × 28 integer weights in `OVR_WEIGHTS` (summed in `OVR_TERMS` order). No anchor, no fitted penalty. `positionTiles` gives all 13 positions; the panel's overall is the tile at the selected position (`BuildResult.tiles`, `BuildResult.overall`). Aptitude coding: database 0 full / 1 half / 2 none (dump inverted).
- **Position tiles / Best Fit / "At POS"** (Pitch Map, `PitchMap tiles`): computed with the formula for every card — from the build when the card has a panel, else from the stats in the grid (level-cap-1 "Max" = base + Booster 1) — never from the stored eFHUB `rating*` columns (kept, reference only: they match the formula at full positions 97.5 % but read 3.1 lower at half and 1.4 lower at none positions). The compare page's position dots use the same function on the level-1 stats.
- **Population check** (no bonus, dump × eFHUB, 2026-10-19): formula on eFHUB max stats + Booster 1 = efootbase `overall_at_max_level` on 9,358/9,843 cards (95.07 %; within 1 98.37 %; GK 92.88 % exact); formula on base stats = the dump overall on 40,479/40,516 level-cap-1 cards (99.91 %, all within 1). ## Known limitations (reported, not hidden)

- **Progression uses efootbase's constants** (`ovrModel.ts`, recovered from efootbase's public client; owner-accepted terms risk) — exact on every reading of the five surveyed cards, checked in bulk elsewhere (95.1 % exact at max level on 9,843 cards fed eFHUB max stats, 99.9 % on the 40,516 level-cap-1 cards); a change of efootbase's constants needs a new survey (`docs/efootbase-exact-model.md`). A stat trained past 99 is cut to 99 before the boosters, like efootbase's sheet (owner decision 2026-10-19; no survey reading reaches it, synthetic tests pin it; the eFHUB population check leans the other way — 94 vs 65 of 99 cards — while the dump's `max_attributes` minus both boosters never exceed 99 on the 10,175 cards with progression). The Max OVR preset ignores the bonus and the cut (up to 1 displayed point below the bonus- and cap-aware best, up to 2 on the 108 cards whose preset trains a stat past 99) and its allocation can differ from efootbase's with the same overall. The picker order inside a rating is by id (efootbase's source order is not stored). Builds and the selected manager are not persisted anywhere (the Build table and `community.saveBuild` were removed). The stored eFHUB position ratings are no longer displayed (they disagree with efootbase off the registered position).
- **Dump freshness** — re-dumped 2026-10-18 (see "2026-10 re-dump" above); the newest `releaseDate` in the DB is 2026-10-15 (was 2026-10-01 with the 2026-10-06 dump; Ricardo Quaresma, base 4526, missing then, is now present). The 2,284 new cards have no eFHUB cross-fill data, overwritten R2 card images may be served stale from caches (1-year immutable), and `time_added` does not move on stat edits. Refreshing again needs `scripts/efootbase_dump.py` + `EFBASE_API_KEY`.
- **efootbase could not be compared on results** — its API sits behind a Cloudflare bot check, so the /players filters, sort presets and search were verified against our own data only; labels and controls follow the 2026-10-18 capture.
- **Position Training / In-Match Roles** — efootbase has them, the dump has no such data; not built.
- **Body Model, Form, Injury Resistance** — stored for every card (`Player.neckLength…legLength`, `legCoverage…dribbleHeight`, `form`, `injuryResistance`; form/injury are 0–2 and efootbase shows value + 1 stars of 3). `player.byId` / `player.compare` (`toCardDTO`) return them as `PlayerCardDTO.physique` (11 ints), `bodyMetrics` (5 floats), `form` and `injuryResistance`; the detail page renders the real values (no migration — the columns were already seeded). The fields are typed optional in the DTO so a caller without them (none today) degrades to the "not exposed" note instead of a placeholder number.
- **Static skill / manager data is a hand-taken snapshot** (2026-10-18, `docs/efootbase-static-snapshot.md`) — it goes stale and is regenerated by hand. Stat boosts exist only for the 28 skills efootbase showed on the cards the survey loaded; a skill without data shows no boost (never a guess). The 5 unreleased skills (Sharp Cut, Beast Drive, Decisive Pass, GK Rush Out, GK Aerial Claim) are stored hidden (`released: false`) with an efootbase description, group (Showtime), `efbKey` and `sortOrder`, but with no icon, no stat effects, no activation and no holders. Third-party descriptions, activation text, icons, manager art and the snapshot JSON live only in `dump/` (git-ignored), the database and R2 — a fresh clone without the snapshot seeds fixture names/descriptions and lists every skill under "Other". **A seed run without `skills.json` erases the skill metadata already loaded** (the Skill table is rebuilt from the fixture inside the seed transaction: efootbase names, descriptions, group, order, icon key, effects and activation are gone until a seed with the snapshot), whereas a seed without `managers.json` leaves `Manager.inPicker` as it is. The stored skill name now follows efootbase (e.g. "One-touch Pass"); `lib/skill-labels.ts` keeps the old label overrides only for a database seeded without the snapshot. The 4 managers added on 2026-10-19 have no tactics until the next `db:crossfill`; after it Makino Tomoaki and R. Rodríguez have their own eFHUB numbers, while the new Klopp and Cristian Chivu cards stay **without tactics** (eFHUB has no entry for their ids and efootbase has no manager tactics; another card's numbers are never copied); 24 of the 69 picker managers have one pill only (`booster_2` null on efootbase).
- **Post-dump skills and playing styles** — efootbase's Skills filter (2026-10-18 capture) lists 28 Showtime skills; 5 of them (Beast Drive, Decisive Pass, GK Aerial Claim, GK Rush Out, Sharp Cut) are not in the dump: they are hidden `Skill` rows (`released: false`), so our Showtime group has 23 and no card can be filtered by them. The AI style "Long Ranger" has no column. The 4 playing styles that post-dated the first dump arrived with the 2026-10 re-dump and are mapped since 2026-10-19 — Press Back 23, Tough Marker 31, Deep Defender 32 (defence slot), Build-up GK 34 (attack slot), named from efootbase's English UI strings because `players_meta.json` still has no label for them; `PLAYING_STYLES_UNAVAILABLE` is empty (the disabled-pill mechanism stays for future styles).
- **40,516 cards have `levelCap` 1** — that is what the dump carries (37,217 of them also have `maxOvr == ovr`; 50,691-card dump of 2026-10-18), not a seeder bug.
- **CJK search** (`japName`/`chineseName ILIKE`) runs only for non-ASCII queries and is not index-backed.
- **Nation filter links carry internal ids** (`nat=14`), not ISO codes — `Country` has no code column; a re-seed that renumbers countries changes what an old link means (see "Multi-valued filters" under Conventions).
- **Kept on purpose after `remove-dead-surface` (2026-10-18)** — not dead by accident, each has an owner decision behind it: the `auth` router + Google OAuth + User/Session/Account (no sign-in UI is routed; `auth.tsx` still calls `getSession`/`signOut`); `protectedProcedure` in `router/trpc.ts` (no mounted procedure uses it since the community routers went); the Pack/PackCard (2,065 / 13,828) and Manager (1,479; 69 `inPicker`, read by `manager.picker` since efootbase-exact-model-managers) tables with their seeding and cross-fill (data assets; the APIs read only the pack name in `player.byId` and the picker rows); `better-auth` (only `better-auth/crypto` is imported); `zod` and `superjson` as direct `apps/api` dependencies (the API imports both through `@eflab/shared`). The R2 bucket still holds the `card-backgrounds/`, `frames/`, `managers/` objects nobody renders.
- **Konami fonts** (`apps/web/public/fonts/eFootballSans-*.ttf`, `eFootballStencil-Regular.ttf`, loaded by `globals.css`) have an unknown licence.
- **Git history still contains the two previously committed third-party keys** (`docs/apk-db-expansion.md`, `docs/efootbase-ui-dna.md`); redaction covers the working tree only.
- **Sync worker limits** (change `admin-sync-worker`, details in `docs/admin-sync.md`):
  - Incremental runs see only new cards (`time_added` does not move on stat edits): edits reach the DB only through the weekly full run; incremental downloads the images of the cards / emblems it inserts and ETag-compares (`--etag-vs-bucket`, needs `R2_PUBLIC_BASE`) those of the known cards it rewrites, replacing only differing ones (counted as overwritten); it never creates Pack rows.
  - Neither run does the eFHUB cross-fill.
  - Overwritten card images need a `DEFAULT_IMAGE_VERSION` bump and a web rebuild by hand (the dashboard warns with the count).
  - The full run's changed-image test assumes R2's single-part ETag = content MD5 (not verified against the real bucket; if wrong, more downloads, never a missed change). The r2.dev public URL is rate-limited, and non-200/404 bucket answers count as "possible overwrite".
  - A full run records the ids whose images it must compare (`stats.imagesPendingIds`, written before its seed; the API sends only `imagesPending`) and removes them when its image step finished; the next full run compares the pending ones again (also after a kill). Its seed child is never stopped by cancel / time limit / worker stop (≤ 70 min), so a full run may outlast 6 h by the seed's rest and the service stop timeout should be 75 min.
  - All stored times are written time-safely — typed Prisma queries, or `jsonb_to_recordset(… timestamp(3))` (the upserts; Postgres ignores the `Z`), never a raw `Date` parameter — so the database's TimeZone does not matter (suites run under America/New_York and Asia/Ho_Chi_Minh).
  - Image failures never stop a run (third verify W1): a failed image, or one skipped because pesdb.net refused (its 403 / 429 / challenge skips only its own images — only efootbase's API / CDN refusals block the source for 6 h), is counted failed and its card owed (`imagesPendingIds`, `imagesChecked`); the next run compares owed images again. "Overwritten" = a body that differs from a bucket object with a content-MD5 ETag (equal bodies are dropped; non-MD5 bucket ETags → `imagesUnverified`) — the only count behind the image-version warning (W2). Bodies need a PNG/WEBP/JPEG/GIF signature (S1).
  - Blocked → 6 h with no request.
  - A full run needs the static snapshot (`skills.json` + `skill-icons/`) and 2 GB free.
  - The worker counts as online for 2 min after its last heartbeat.
  - `trustProxy` is unset, so behind a proxy the per-address sign-in limit is global.
  - The admin cookie is SameSite=Strict: web and API must be the same site.
  - With the default root `.env` the key and R2 credentials are also present, unread, in the API / Next environment — the strict split is a separate worker env file.
  - Admin code adds ~1 KB gzip to the public First Load JS (shared-chunk split, no duplicated code).
- **No CI** — `pnpm typecheck` and `pnpm test` are run by hand.
