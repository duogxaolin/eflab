## What this is

**eflab** = "eFootLab" — a fan-made eFootball player database: every card with real stats, side-by-side compare, the latest packs and the full skill list. Turborepo + pnpm monorepo. Not affiliated with Konami; all player data comes from public third-party dumps (efootbase API dump as primary, eFHUB CDN SQLite as secondary cross-fill).

**The GitHub repo `duogxaolin/eflab` is PUBLIC** (`main` is pushed). Never commit secrets, `dump/`, database backups, Konami assets or audit reports. Two third-party keys were committed in `docs/` before 2026-10-17; they are redacted in the working tree but **still exist in git history** — on 2026-10-27 the owner decided to keep them there and accept the risk (no history rewrite; rotation is the key owners' side; see "Known limitations").

This repo is **distinct from the `bno` bot** (a separate eFootball scraper the user also runs). Data-source decisions for bno live in memory under `bno-bot-data-decision`. **Don't conflate the two** — bno uses pesdb images and efhub data; eflab uses the card renders the efootbase dump links to, mirrored to R2 — mostly efootbase's CDN, but the dump's `transparent` render is a pesdb.net image for 36,872 of the 50,818 cards of the 2026-10-24 dump (the sync worker fetches those from `pesdb.net/assets/img/` only).

## Player data pipeline

Player data is **not** self-datamined from the game (see `docs/efootball-apk-datamine-analysis.md`). Source of truth is the **efootbase dump**, with **eFHUB** as a secondary cross-fill.

1. **Dump** — `scripts/efootbase_dump.py` (needs `EFBASE_API_KEY`; the script reads it from the `.env` passed with `--env`, default an APK-extract path) → `dump/efootbase/players.jsonl` (50,818 cards, 176 distinct keys — 173–176 per row —, re-dumped 2026-10-24), `players_meta.json` (field labels, card-type labels), `packs.json` (featured bundles), `teams.json`, `manifest.json` (`dumpedAt` — the seed stores it as `CatalogueMeta.playersDumpedAt`), `images/` (97,538 card + 1,022 emblem files, ~6.5 GB). `dump/` is gitignored; the 2026-10-18 data files are kept in `dump/efootbase-2026-10-18/`. See memory `efootbase-datapath`.
2. **Seed** — `pnpm db:seed` (`packages/db/src/seed-efootbase-full.ts`). **Non-destructive upsert in ONE interactive transaction** (60-min timeout): Player and Manager are `INSERT … ON CONFLICT DO UPDATE` over a column list generated from the Prisma model minus `PLAYER_CROSSFILL_COLUMNS` / `MANAGER_CROSSFILL_COLUMNS`, so cross-fill-owned columns are **never written by the seed**. Country/League/Team/Pack/PackCard/Skill/PlayerSkill/FeaturedBundle(+Card) are replaced inside the same transaction (no FK reaches a user table). Booster is upserted by id (dump wins over fixtures). User tables (User/Account/Session) are untouched unless `--reset-users`; players missing from the dump are kept and logged unless `--prune`. The JSONL is streamed twice (lookups, then writes). Field mapping uses the dump's real keys: `jumping→jump`, `set_piece_taking→placeKicking`, `tackling→ballWinning`, `pos→registeredPosition`, `condition` via `[E,D,C,B,A]`, `injury_resistance`, `player_value→marketValue`, `leg_length_height→dribbleHeight`, `name_normalized→nameNormalized`, `league→leagueId` (the card's **own** league, stored only when that League id exists, else NULL — `cardLeagueId`), `avgRating` / `ratingCount` / `views` (same names). The seed also writes `CatalogueMeta` (single row: `playersDumpedAt` = the manifest's `dumpedAt` next to `players.jsonl` when it is strict ISO-8601 UTC — otherwise the stored value is kept with a notice —, `seededAt`) and `Manager.pickerOrder` (below). Unmatched `s_*` skill keys, card-type codes that disagree with `players_meta.json`/pack names, and unknown booster stat keys abort the seed. Position ratings (`ratingGK…ratingCF`) are nullable and left null by the seed. The row mapping and the column-list upsert live in `efootbase-map.ts` / `upsert.ts`, shared with the sync worker (moved unchanged in change `admin-sync-worker`; the seed's output was proven identical on two scratch copies of the live database).
3. **Cross-fill** — `pnpm db:crossfill` (`packages/db/src/seed-efhub-crossfill.ts`) reads `dump/efhub/efhub_db.sqlite` through the `sqlite3` CLI (`SQLITE3_BIN`, ServBay: `/Applications/ServBay/bin/sqlite3`; `EFHUB_DB_PATH` overrides the file). Writes only what efootbase cannot expose: Manager tactic ratings (exact-id merge, then name merge with `ALIASES` — skipped when the name's best eFHUB entry is another Manager row's card, so a new card never copies another card's tactics — then create; 1,476 managers with tactics after the 2026-10-24 refresh), `Player.stars/reputation/overallPotential/gkClearing/maxGkClearing`, the 13 `ratingGK…ratingCF` from eFHUB `overallGK…overallCF` (reference only — the web computes position values with the exact formula), `communityTier` (10,745 tier badges), and 3 eFHUB-only players (ovr/maxOvr 40 placeholders). `registeredPosition` is seed-owned (dump `pos`); the cross-fill only reports mismatches. All SQL uses bound parameters. Idempotent.
4. **`pnpm db:refresh` = `db:seed` then `db:crossfill`** — the documented refresh. A standalone `db:seed` keeps earlier cross-fill values but cannot add them; it prints that notice.
5. **Verify** — `python3 -I scripts/verify-seed.py` streams the dump and compares it with the DB over read-only psql (`PGOPTIONS=-c default_transaction_read_only=on`); exit 1 on any mismatch. It also checks the static snapshot (below) when `dump/efootbase/static/` exists. Its manager-duplicate check reads the eFHUB SQLite read-only (`--efhub-db`, default `EFHUB_DB_PATH` / `dump/efhub/efhub_db.sqlite`) to tell cross-fill work still pending after a seed (info) from real duplicates (failure); run it with `--after-crossfill` right after `pnpm db:refresh` so pending rows fail too. Since change `efootbase-data-refresh-1024` it also checks: `Player.leagueId` = the dump's `league` when the League table holds it, else NULL (the NULL count is printed as info), the League rows = `fixtures/leagues.json`, `avgRating` / `ratingCount` / `views` = the dump, `CatalogueMeta` (one row, `seededAt` set, `playersDumpedAt` = the manifest's `dumpedAt`) and `Manager.pickerOrder` = the index in the static `managers.json` (NULL outside the picker). ## Known limitations (reported, not hidden)

- **Progression uses efootbase's constants** (`ovrModel.ts`, recovered from efootbase's public client; owner-accepted terms risk) — exact on every reading of the five surveyed cards, checked in bulk elsewhere (95.1 % exact at max level on 9,843 cards fed eFHUB max stats, 99.9 % on the 40,516 level-cap-1 cards — 2026-10-18 dump, not re-run on the 2026-10-24 data); a change of efootbase's constants needs a new survey (`docs/efootbase-exact-model.md`).
